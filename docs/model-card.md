# Карточка модели: задержка на остановке через 10–15 минут

ML-ядро системы: что модель делает, на чём училась, насколько точна, как
быстро отвечает и где ошибается. Обоснования и все замеры —
`docs/specs/ml-model.md`, команды — `ml/README.md`.

## Что делает

По телеметрии автобуса до момента `T` и его плану на день модель
прогнозирует задержку на первой остановке, до которой по плану от 10 до
15 минут. Ответ на каждый запрос:

- `prediction_s` — задержка в секундах, со знаком (минус — раньше плана);
- `p_late` — вероятность опоздать больше чем на 2 минуты;
- `reasons` — до трёх причин опоздания, самая сильная первой.

Модель работает в сервисе `predictor` (`POST /predict`, контракт —
`packages/contracts`). Сабмит по validate считается тем же кодом:
`busdelay.inference.Forecaster`, точки validate превращаются в такие же
запросы, какие шлёт `api`.

## Две модели

| | Сабмит `submit_v2` | Сервис `models/current` |
| --- | --- | --- |
| Что это | CatBoost, лосс MAE: остаток над двумя прямыми | Среднее двух CatBoost: остаток и задержка целиком |
| Подсказка `cur_dev_s` | организаторов | обе: организаторов и оценка по GPS |
| Настройки | depth 4, l2 30, lr 0.03, среднее 5 сидов | остаток — как у сабмита; задержка целиком — depth 6, l2 3 |
| Вероятность опоздания | классификатор, AUC 0.83 | среднее двух классификаторов, AUC 0.80 на подсказке по GPS |
| Размер | 2.5 МБ | 6.9 МБ, лежит в git |

Моделей две, потому что на живом потоке подсказки организаторов нет:
`cur_dev_s` сервис оценивает по GPS сам, а модель, обученная только на
хорошей подсказке, с оценкой по GPS ошибается заметно сильнее (86.4 с
против 79.0 у `current` на test).

«Две прямые» — наш бейзлайн: `a · cur_dev_s + b` отдельно для точек, у
которых до цели есть отстой на конечной, и для остальных. Модель учит
поправку к нему.

## Данные

- Один день, 6 января 2026: 13 настоящих автобусов, 1494 размеченные
  точки в train и test, 151 точка в validate.
- 26 синтетических автобусов из train в обучение не идут. Это копии
  настоящих со сдвигом по времени; модель с ними списывает задержку у
  «двойника», а на незнакомом маршруте почти не лучше двух прямых
  (разбор — в спеке, «Синтетические двойники»).
- Фактические времена из расписания в признаки не идут: прошлые прибытия
  восстанавливаются по GPS, как на потоке. Телеметрия — только до `T`.

## Признаки

43 признака, одна функция на офлайн и поток (`features.point_features`):

- расписание: сколько до цели по времени, остановкам и расстоянию; отстой
  впереди; место цели в рейсе; час;
- подсказка `cur_dev_s` и запас отстоя после вычета опоздания;
- движение за 5–15 минут: скорость, доля времени стоя, сколько стоит
  сейчас, свежесть сигнала;
- задержки на пройденных остановках по GPS: последняя, средняя, тренд;
- прошлый круг: задержка на той же остановке кругом раньше.

## Качество

MAE в секундах на настоящих автобусах. CV — 5 фолдов, отрезок пути
автобуса целиком в одном фолде, среднее трёх разбиений. «По бортам» —
автобус целиком в одном фолде. Контроль — обучение на train, проверка на
test.

| Прогноз | CV | CV по бортам | контроль на test |
| --- | ---: | ---: | ---: |
| ноль | 93.0 | — | 103.3 |
| persistence (`cur_dev_s`) | 88.4 | — | 93.4 |
| две прямые | 72.9 | 73.2 | 80.0 |
| **`submit_v2`** | **65.4** | **70.1** | **70.7** |

Скор на платформе: две прямые — 0.688, `submit_v2` — **0.839**.

Сервис на потоке, `cur_dev_s` по GPS:

- `current` на CV: 73.4 (две прямые с той же подсказкой — 87.2,
  persistence — 128.8);
- вся система в Docker, test проигран через шину с контрольной моделью
  (обучена только на train): 81.6 против 97.2 у двух прямых и 143.4 у
  persistence на 1388 прогнозах;
- у `current` на CV в 80% точек факт лежит в пределах от прогноза −105 с
  до прогноза +126 с.

## Причины

Вклады SHAP по группам признаков. В ответ попадают группы, которые
добавляют к прогнозу не меньше 15 с.

| Причина | Код в ответе |
| --- | --- |
| накопленное опоздание | `accumulated_delay` |
| медленное движение на подходе | `slow_approach` |
| долгая стоянка | `long_dwell` |
| на прошлом круге здесь опаздывал | `low_speed_segment` |
| нестабильный сигнал или старая позиция | `stale_telemetry` |
| отстой на конечной, расписание | `unknown` (в контракте нет кода) |

На проигрывании test у 99% прогнозов опоздания больше 2 минут (1327
штук) есть причина помимо `unknown`.

## Скорость

- `predictor`, 13 автобусов в одном запросе с телеметрией за 150 минут
  (1.8 МБ JSON): медиана 379 мс, из них сам прогноз — около 300 мс.
- Вся система, от точки в шине до опубликованного прогноза: медиана
  214 мс, максимум 404 мс при таймауте `api` в 1 с.
- `docker compose up -d --wait` с пустой базой и собранными образами —
  16–18 с; `predictor` после перезапуска отвечает через 3.5 с. Памяти
  занимает 260 МБ.

## Отказы

- Модели нет или она битая — сервис поднимается и отвечает бейзлайном
  организаторов (`model_version: baseline`), `GET /model` говорит почему.
- На точку, для которой признаки не строятся, сервис отвечает
  бейзлайном, на остальные точки пачки — моделью.
- Телеметрия оборвалась или идёт без координат — модель прогнозирует по
  последнему состоянию и добавляет `stale_telemetry`. При обрыве до
  15 минут она остаётся лучше двух прямых на 10–14 с.
- `predictor` недоступен — `api` отвечает бейзлайном и сам возвращается к
  модели, когда сервис поднимется (проверено остановкой на 20 с).

## Ограничения

- Данные — один день. Признаки места и времени (час, номер рейса,
  координаты цели) — это знание об этом дне; без них CV хуже на 1.4 с.
  Для другого дня модель нужно переобучить на истории.
- Оценка `cur_dev_s` по GPS в 9% точек ошибается больше чем на 5 минут,
  почти всегда на конечной. Если подсказка от `matcher` окажется точнее,
  на неё переключает одна строка конфига
  (`predictor.cur_dev_source: request`).
- Если за все 150 минут нет ни одной позиции, модель хуже двух прямых на
  7 с. В данных такая точка одна из 1494.
- Проверено на 13 автобусах. Время прогноза растёт примерно на 25 мс с
  каждым автобусом в запросе, так что в таймаут `api` в 1 с по оценке
  помещается около 35. Для большего парка пачку нужно делить или
  добавлять воркеры `predictor`.

## Как проверить

**Swagger ML-ядра** — <http://localhost:8003/docs> при поднятом compose:

1. `POST /predict` → Try it out. В поле примеров уже выбран «A bus
   4 minutes late» — выдуманный автобус, опаздывающий на 4 минуты.
2. Execute. Ответ: `prediction_s` около 245, `p_late` около 0.80,
   причины `accumulated_delay` и `slow_approach`, `model_version`
   начинается с `current@`.
3. `GET /model` — какая модель загружена, откуда берётся `cur_dev_s`, MAE
   на кросс-валидации.

**Сабмит с нуля** — из `ml/`, датасет распакован в `data/dataset/`
(установка — `ml/README.md`):

```
python -m busdelay features
python -m busdelay train --name submit_v2 --hint given
python -m busdelay predict --model ../models/submit_v2
```

Несколько минут на CPU. Получается `data/submissions/submit_v2.csv`;
`predict` сам проверяет его формат. У нас переобучение с нуля дало
побайтно тот же файл, что загружен на платформу (sha256 начинается с
`9fa149fb`).
