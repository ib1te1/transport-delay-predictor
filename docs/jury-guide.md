# Проверка решения: инструкция для жюри

Система прогнозирует отклонение автобуса от расписания на первой остановке,
запланированной через 10–15 минут после текущего времени данных. Решение
состоит из ML-сервиса `predictor`, бэкенда (`ingest`, `matcher`, `api`) и
диспетчерского дашборда `web`.

## Подготовка

Нужны Docker Compose и раздача организаторов в `data/dataset/`: в частности,
`validate/traffic.csv`, `validate/schedule_plan.csv` и `validate/points.csv`.
Датасет не входит в Git. Все команды ниже выполняются из корня репозитория.

## Сценарий А: сквозной прогноз по историческому потоку

На Windows для повторяемого показа запустите:

```powershell
.\scripts\start-demo.ps1
```

Скрипт удаляет **состояние локального демо** (том Postgres и данные Redis),
собирает и поднимает сервисы, затем запускает проигрыватель в фоне. Исходные
файлы `data/dataset/` сохраняются. На Linux/macOS эквивалентные команды:

```bash
docker compose --profile '*' down -v
docker compose up --build --wait --wait-timeout 300
docker compose --profile replay up -d replay
```

По умолчанию проигрывается часть `validate` с 11:30 до 18:00 UTC с ускорением
×10 — около 39 минут реального времени. Дашборд открывается сразу, а примерно
через три минуты накопится 30 минут истории и появятся прогнозы. Не меняйте
`seed.period` отдельно от `replay.period`: расписание и телеметрия должны
относиться к одному периоду.

1. Откройте <http://localhost:5173/>. Верхняя строка показывает состояние
   подключения и **время данных в UTC**; список и карта обновляются вслед за
   потоком. У ТС без координат остаётся запись в списке.
2. Фильтр «Высокий риск» выделяет красные прогнозы. Открытые предупреждения
   видны рядом с заголовком и в панели «Инциденты»; выберите инцидент.
3. Карточка ТС показывает прогнозируемое отклонение, вероятность опоздания,
   целевую остановку, плановое время, причины и признак резервного расчёта.
   Инцидент дополнительно показывает участок маршрута и время открытия.
4. На карте показаны ТС, плановая последовательность остановок выбранного
   рейса и его недавний GPS-трек. Прямые между остановками — схема плана,
   **не дорожная геометрия**. Жёлтый пунктир отмечает GPS-отрезки дальше
   трёх километров от плановых остановок; разрыв трека означает отсутствие
   телеметрии более двух минут. Подложка OpenStreetMap включается отдельно;
   без интернета карта, маркеры, план и трек продолжают работать.
5. Для проверки API откройте <http://localhost:8000/docs>, снимок
   <http://localhost:8000/api/state>, алерты <http://localhost:8000/api/alerts>
   и метрики <http://localhost:8000/metrics>. Swagger ML-сервиса —
   <http://localhost:8003/docs>, сведения о модели —
   <http://localhost:8003/model>, время ответа —
   <http://localhost:8003/metrics>.

Исторический CSV поступает в `ingest` через проигрыватель и далее проходит
Postgres → Redis Streams → `matcher` → `api` → `predictor` → дашборд.
**Этот сценарий не декодирует NDTP**: раздача CSV уже содержит раскодированную
телеметрию. Пример повторного запуска находится также в [README](../README.md).

## Сценарий Б: приём NDTP по TCP

NDTP-парсер проверяется отдельно, поскольку эмулятор посылает случайные
координаты, не соответствующие реальному маршруту из CSV. Сначала завершите
сценарий А. Установите в `config/system.yaml` `ingest.mode: emulator` и
`ingest.ndtp.dataset_anchor` на время выбранного периода (например,
`2026-01-06T12:30:00Z`), затем выполните:

```bash
docker compose down -v
docker load -i data/dataset/ndtp-telemetry-emulator.tar
docker compose --profile emulator up --build -d
curl http://localhost:18080/api/cells
```

Отправьте конфигурацию эмулятору через `POST http://localhost:18080/api/config`:
`targetHost` = `ingest`, `targetPort` = `9201`, а `unitId` возьмите из
`validate/traffic.csv` для автобуса, присутствующего в расписании. Пример
JSON и команды — в [README](../README.md#подача-телеметрии). Эмулятор
подключается по TCP, повторно подключается после обрыва, а координаты
доходят до списка и карты. Случайные координаты эмулятора не подходят для
оценки точности прогнозирования задержки.

## Качество и ограничения

- Для честного сабмита `submit_v2` зафиксирован скор платформы **0,839**;
  воспроизведение и проверка входных данных описаны в
  [карточке модели](model-card.md). Онлайн-модель использует собственную
  оценку текущего отклонения по GPS, поэтому её качество измеряется отдельно.
- [Замер всей системы](performance.md) на полных сутках `validate` при ×60 и
  150-минутной истории: p95 «телеметрия → прогноз» 296 мс, p95 ответа
  ML-сервиса 213 мс; отказ
  `predictor` переводит `api` на резервный прогноз и восстановление не
  требует перезапуска `api`.
- Данные охватывают один день и небольшой парк; для другого дня модель
  потребуется переобучить. Демо использует 30 минут истории ради быстрого
  запуска; полные 150 минут улучшают MAE на test примерно на 4 секунды.
- Код сервиса снабжён Sphinx-справочником: исходники в
  [docs/code](code/index.rst), команда сборки в [README](../README.md#документация-по-коду).
  OpenAPI доступен по адресам Swagger выше.
- Сторонние материалы и условия использования перечислены в
  [реестре](third-party.md).
