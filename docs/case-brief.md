## Кейс: предиктор изменений в графике движения городского транспорта

### Краткое описание

Точное соблюдение графика движения — главная метрика качества наземного
пассажирского транспорта. Задача — разработать ИИ-систему для раннего
прогнозирования изменений в движении транспорта за 10–15 минут до
фактического наступления задержки. Система непрерывно анализирует
потоковые телематические данные (формат NDTP), сопоставляет их с эталонным
расписанием, выявляет паттерны сбоев и визуализирует проблемные участки на
дашборде диспетчера. Это позволяет перейти от реактивного управления к
проактивному.

### Проблематика

Диспетчерские службы реагируют на инциденты постфактум: если ТС уже
опоздало или сбилось с интервала, остаётся констатировать факт и
«догонять» график, что вызывает эффект домино по всему маршруту. Нет
инструментов раннего предупреждения — отсюда падение качества перевозки,
нерациональное использование подвижного состава и невозможность
упреждающих мер (выпуск резервного ТС, изменение схемы объезда,
корректировка интервалов на светофорах).

### Образ решения

Комплексное приложение из вычислительного ML-модуля, Backend-сервиса и
BI-дашборда. Система в реальном времени потребляет телеметрию, накладывает
её на нитку графика, с помощью ML-моделей вычисляет вероятность отклонения
в горизонте 10–15 минут, определяет паттерн/причину сбоя и выводит алерт на
экран диспетчера с рекомендациями.

### Ключевые требования

- Горизонт прогнозирования строго 10–15 минут до наступления события.
- Разделение архитектуры на независимые модули: Backend (API, оркестрация)
  и ML-модуль (инференс/обучение).
- Понятный и информативный интерфейс для принятия решений диспетчером.

### Функциональные требования

**Анализ и обработка потоковых данных**

- Непрерывный приём и парсинг потоковых телематических данных в формате
  NDTP (от эмулятора и исторического датасета).
- Сопоставление телематических данных (координаты, скорость, статус
  дверей) с эталонным историческим и текущим расписанием.
- Очистка данных и расчёт производных признаков (отклонение от графика на
  текущий момент, средняя скорость на сегменте, время простоя).

**Предиктивное моделирование (ML-ядро)**

- Прогнозирование вероятности задержки ТС в горизонте 10–15 минут.
- Расчёт абсолютной ошибки прогнозируемого времени отклонения.
- Выявление паттернов поведения ТС, предшествующих сбою (например,
  аномальное снижение скорости на подходе к перекрёстку, длительное время
  посадки).

**Диспетчерский BI-дашборд**

- Визуализация маршрутной сети с наложением текущего положения ТС.
- Цветовая индикация уровня риска на маршрутах (зелёный/жёлтый/красный).
- Карточка инцидента: ТС с высокой вероятностью задержки, прогнозируемое
  время опоздания, предполагаемая причина и участок маршрута.

### Общие требования (рекомендация, а не жёсткое правило)

- Архитектура: чётко выделенные модули — Backend (web-сервис) и
  вычислительный модуль машинного обучения.
- Стек и сборка: Python 3.12+, PyTorch, CatBoost. Обязательна упаковка в
  Docker-контейнеры.
- Документация: сгенерированная документация по коду (PyDoc/Sphinx) и
  спецификация API (OpenAPI/Swagger).

### Нефункциональные требования

- Производительность: низкая задержка обработки предиктов для потока ТС,
  чтобы диспетчер видел картину в реальном времени.
- Надёжность: корректная обработка обрывов связи с эмулятором, деградация
  (работа по историческим данным или последнему известному состоянию) без
  падения сервиса.
- Масштабируемость: ML-модуль допускает дообучение на новых данных и
  масштабирование инференса.
- Использование ресурсов: приветствуется использование GPU для обучения
  и/или инференса нейросетей.

### Дополнительные фичи

- Map Matching координат на маршрутную сеть с учётом специфики NDTP.
- What-if анализ на дашборде (например, влияние выпуска дополнительного ТС
  на график).
- Оптимизация инференса (квантование, ONNX, TensorRT).
- Ансамбли моделей (например, CatBoost для табличных признаков и
  PyTorch/Transformer для последовательностей телеметрии).

**Критерий 3.**

- Решение упаковано в Docker-контейнеры и поднимается по одной инструкции.
- Чётко выделены ML-ядро (инференс/обучение) и Backend (API, оркестрация) —
  не монолит; API работает (Swagger отвечает на пробный запрос).
- Backend принимает и парсит поток телеметрии NDTP, сопоставляет с
  расписанием и считает производные признаки (текущее отклонение, средняя
  скорость на сегменте, время простоя).
- Связь модулей рабочая end-to-end: поток → прогноз → дашборд.

**Критерий 4.**

- Понятность за ~5 секунд: диспетчер видит проблемные ТС/участки без
  инструкции.
- Карта маршрутной сети с текущим положением ТС и цветовой индикацией риска
  (зелёный/жёлтый/красный).
- Карточка инцидента: ТС с высокой вероятностью задержки, прогнозируемое
  опоздание, предполагаемая причина, участок маршрута.
- Данные обновляются в реальном времени вслед за потоком.

**Критерий 5.**

- Latency инференса низкая (ориентир < 1–2 с на поток ТС); честная оценка
  с подтверждением метриками засчитывается без полного нагрузочного теста.
- Пропускная способность: поток ТС обрабатывается без накопления очередей.
- Деградация при обрывах связи: сервис не падает, переходит на исторические
  данные / последнее состояние и восстанавливается после реконнекта.
- Холодный старт Docker-контейнеров предсказуем. Балл снижается при
  отсутствии подтверждений, но не обнуляется при корректной архитектуре.

1. **Раздел «Data Science»** — csv-файл с прогнозами. Лимиты на команду в

   результат за всё время.
2. **Раздел «Загрузка решения»** — поля формы (ссылки / текст). Обновлять
   можно до **27 сентября, 23:59 МСК**; на проверку идёт последняя версия.

Обязательные артефакты:

- сабмит (.csv) с прогнозами по validate для автопроверки MAE;

## Датасет

По README раздачи.

### Постановка

По потоковой телеметрии за 10–15 минут до события спрогнозировать
отклонение от графика и сформировать `submission.csv`. Метрика — MAE
(секунды).

Прогнозная точка — пара `(tr_id, T)`: известна вся телеметрия ТС до
момента `T`. Предсказать нужно **фактическую задержку** в секундах на
первой остановке этого ТС, чьё **плановое** время прибытия попадает в окно
`(T+10 мин, T+15 мин]`. Целевая остановка и её плановое время даны
(`target_stop_id`, `target_time_begin`).

- Задержка = факт − план: плюс — опоздание, минус — опережение.
- **Правило честности:** для точки `T` используются только данные,
  доступные на момент `T` — телеметрия с `event_time ≤ T` и подсказка
  `cur_dev_s`.
- `train/` и `test/` даны с разметкой (`labels/`). Для `validate/` — только
  входные данные; фактических задержек по validate нет и не будет. Проверка
  идёт по скрытому эталону на стороне платформы.

### Схема файлов

**`traffic.csv`** — телеметрия, разделитель `,`, UTF-8, ~12–15 с между
точками.

| Колонка | Смысл |
| --- | --- |
| `tr_id` | ID ТС (ключ связи с расписанием и разметкой) |
| `event_time` | время телеметрии |
| `location_valid` | достоверны ли координаты |
| `lon`, `lat`, `alt` | долгота, широта, высота |
| `speed`, `heading` | скорость (км/ч), курс (°) |
| `unit_id`, `gps_time`, `receive_time`, `packet_id`, `device_event_id`, `is_hist_data` | служебные |

**`schedule.csv`** (в validate — `schedule_plan.csv` без факта).

| Колонка | Смысл |
| --- | --- |
| `tt_action_item_id` | ID планового прибытия на остановку (= `target_stop_id`) |
| `tr_id` | ID ТС |
| `time_begin` | плановое время прибытия |
| `time_fact_begin` | фактическое время прибытия (нет в validate) |
| `geom`, `building_address` | точка и адрес остановки |

**Прогнозные точки** — `labels/*.csv` и `validate/points.csv`.

| Колонка | Где | Смысл |
| --- | --- | --- |
| `sample_id` | везде | уникальный ID точки |
| `tr_id` | везде | ID ТС |
| `T` | везде | момент прогноза |
| `target_stop_id` | везде | ID целевой остановки |
| `target_time_begin` | везде | плановое прибытие на целевую остановку |
| `cur_dev_s` | везде | подсказка: задержка на последней пройденной остановке, известна на `T` |
| `target_delay_s` | только labels | TARGET: фактическая задержка, с |
| `target_class` | только labels | справочно: `early` / `ontime` / `late`, пороги −60 с / +120 с |

### Формат сабмита

Разделитель `;`, UTF-8, заголовок обязателен, ровно две колонки
`sample_id;prediction`. Нужны все `sample_id` из `validate/points.csv`, без
дублей и пропусков. `prediction` — задержка в секундах со знаком.

### Метрика

```
MAE      = mean(|факт − прогноз|)
mae_zero = mean(|факт|)
score    = max(0, min(1, (mae_zero − MAE) / (mae_zero − MAE_TARGET)))
```

Baseline «прогноз = `cur_dev_s`» даёт скор ≈ 0.40; нулевой прогноз — 0.

### Особенности данных

- Кодировка UTF-8; данные — разделитель `,`, сабмит — `;`.
- Реальные задержки невелики: медиана ~25 с, максимум ~11 мин.
- Не у всех ТС в `traffic.csv` есть прогнозные точки: часть дана как
  дополнительный контекст.
- В train добавлены синтетические ТС; test и validate полностью реальные.

### Эмулятор NDTP

CSV — уже раскодированная телеметрия: строка `traffic.csv` соответствует
навигационной ячейке `G6CellNav00`. Для обучения эмулятор не нужен; он
нужен для real-time части: поднимает живой NDTP-поток для отладки приёма,
парсинга и онлайн-инференса. Онлайн-часть — дополнительный контур поверх
той же модели.

Эмулятор принимает конфиг по REST (порт 18080) и сам подключается по TCP к
NDTP-серверу (`targetHost:targetPort`) как бортовой терминал: handshake,
затем периодические realtime-пакеты. Полная спецификация протокола и
конфига — в документе раздачи.

| Колонка CSV | Поле NDTP | Преобразование |
| --- | --- | --- |
| `event_time` / `gps_time` | `timestamp` | Unix-секунды → datetime |
| `lon` | `longitude` | `/ 1e7`, знак из `extraDopBit6` (E/W) |
| `lat` | `latitude` | `/ 1e7`, знак из `extraDopBit5` (N/S) |
| `alt` | `altitude` | метры |
| `speed` | `speedAvg` | км/ч |
| `heading` | `course` | градусы |
| `location_valid` | `extraDopBit7` | флаг достоверности координат |
| `unit_id` | `peerAddress` (`unitId`) | ID бортового терминала |

## Ответы организаторов

Приведены по смыслу, близко к исходным формулировкам.

- **Виды транспорта.** Решение делается на данных по автобусам; в
  дальнейшем может быть масштабировано на другие виды НГПТ.
- **Внешние данные** использовать можно, с оговоркой на п. 9.4 Положения:
  используемые открытые ПО, библиотеки, модели, датасеты и иные сторонние
  материалы указываются в итоговой документации, условия их лицензий
  соблюдаются.
- **Готовые наработки.** Само решение создаётся в рамках хакатона; личные
  наработки использовать можно.
- **Сторонние сервисы** (пробки, погода) использовать можно.
- **Решение validate по данным.** Получать ответы для validate
  математически из выданных данных, а не прогнозом модели, — нечестно.
