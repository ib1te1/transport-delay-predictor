# Матчер остановочных событий

Решение использует геометрический детектор из подготовительной реализации,
адаптированный к уже работающим ингесту, расписанию и API. Опорный вход —
таблица `telemetry`: ингест сначала сохраняет точку, затем отправляет её в
Redis и отмечает `published_at`. Матчер читает опубликованные строки строго
по `id`. Это даёт порядок и восстановление после сбоя без зависимости от
времени хранения Redis Stream `telemetry`. Он не обрабатывает более позднюю
строку, пока предыдущая ещё ожидает публикации. Повторная доставка ингестом
не создаёт новое прибытие: checkpoint отбрасывает старые времена борта.

Расписание берётся из таблицы `stops_plan`, которую уже заполняет `seed`.
Фактическое время из CSV не используется. Внутренние строки идентификаторов
детектора соответствуют числовым `tr_id` и `stop_id`; внешние контракты
`packages/contracts` не меняются. Если у точки нет `tr_id`, используется
привязка `unit_id → tr_id` из `vehicles`. Если привязки или плановых
остановок нет, точка пропускается с записью в журнале. Время берётся из
`TelemetryRecord.event_time`: оно уже нормализовано ингестом в UTC.

Детектор рассматривает посещения в пределах дня и соседних суток, требует
однозначной остановки в радиусе, регистрирует первое медленное прибытие.
Быстрый проезд восстанавливается только при выходе из радиуса;
`available_at` фиксирует момент, когда событие стало известно. Разрыв GPS
больше `stale_after_sec` не создаёт выдуманное отправление. Все пороги,
которые зависят от данных, находятся в `config/assumptions.yaml`.

Позиция чтения, checkpoint каждого ТС, событие и запись для публикации
сохраняются одной транзакцией Postgres. Исходное прибытие не дублируется при
отправлении: обновляется только `departure` в таблице. Redis Stream
`stop_events` получает общий `StopEvent` через `common.bus`, поэтому API
читает его существующим кодом. Outbox гарантирует повтор при недоступности
Redis; возможный повтор после сбоя между XADD и коммитом безопасен для API,
который хранит последнее событие по `tr_id/stop_id`.

Миграция `0004` продолжает цепочку ингеста `0003`. PR матчера основан на
ветке ингеста и должен сменить базу на `main` после её слияния. Применять
миграцию к пустой БД и проверять с работающими Postgres и Redis в CI.

Ограничение: значения checkpoint детектора зависят от порогов. Изменение
порогов после обработки данных требует нового воспроизведения; несовместимый
checkpoint не сбрасывается молча. Новый прогон всего демо после завершённого
прогона требует согласованного сброса состояния API и Redis Stream, который
сейчас не реализован во всей системе.
