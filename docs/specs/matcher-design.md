# Матчер остановочных событий

Решение использует геометрический детектор из подготовительной реализации,
адаптированный к уже работающим ингесту, расписанию и API.

## Вход

Матчер читает `TelemetryRecord` из Redis Stream `telemetry` командой
`XREAD` пачками (`matcher.batch_size`) от сохранённого id записи. Id
записей в потоке монотонны, поэтому строка, которую ингест закоммитил не
по порядку, не теряется, а таблицы ингеста матчеру не нужны. Поток
ограничен примерно 200 тыс. записей (`STREAM_MAXLEN` в `common.bus`), а
весь `test/traffic.csv` — около 106 тыс. строк, так что прогон части
датасета помещается в поток целиком. Шина доставляет запись как минимум
один раз: повтор отбрасывается детектором как точка со старым временем.

`tr_id` берётся из записи, а если его нет — из привязки `unit_id → tr_id`
таблицы `vehicles`, которая читается при старте. Точки неизвестного ТС,
ТС без плана, без валидной координаты и нечитаемые записи пропускаются;
счётчики видны в `/quality`. О неизвестном ТС, ТС без плана и нечитаемой
записи журнал сообщает один раз. Время — `TelemetryRecord.event_time`,
ингест уже привёл его к UTC.

Расписание берётся из таблицы `stops_plan`, которую заполняет `seed`.
Фактическое время из CSV не используется. Внутренние строки
идентификаторов детектора соответствуют числовым `tr_id` и `stop_id`;
внешние контракты `packages/contracts` не меняются.

## Детектор

Детектор рассматривает посещения в пределах дня и соседних суток, требует
однозначной остановки в радиусе, регистрирует первое медленное прибытие.
Быстрый проезд восстанавливается только при выходе из радиуса;
`available_at` фиксирует момент, когда событие стало известно. Разрыв GPS
больше `stale_after_sec` не создаёт выдуманное отправление. Все пороги,
которые зависят от данных, находятся в `config/assumptions.yaml`.

Один детектор на все ТС живёт в памяти: при старте в него загружаются
весь `stops_plan` и сохранённые состояния ТС из `matcher_state`.

## Сохранение и доставка

Пачка обрабатывается одной транзакцией Postgres: позиция в потоке
(`matcher_cursor.stream_id`), состояние затронутых ТС, события и записи
outbox. Если транзакция не прошла, память детектора может опережать базу,
поэтому детектор сбрасывается, заново загружается из базы и читает ту же
пачку ещё раз. Исходное прибытие не дублируется при отправлении:
обновляется только `departure` в таблице.

Redis Stream `stop_events` получает общий `StopEvent` через `common.bus`,
поэтому API читает его существующим кодом. Outbox гарантирует повтор при
недоступности Redis; возможный повтор после сбоя между XADD и коммитом
безопасен для API, который хранит последнее событие по `tr_id/stop_id`.

## Пороги и новый прогон

Пороги сохраняются вместе с позицией в `matcher_cursor.settings`. Если
значения в `config/assumptions.yaml` не совпадают с сохранёнными, сервис
не стартует: в журнале — какие значения сохранены и какие заданы, и
подсказка вернуть прежние или выполнить `scripts/reset-demo.sh`
(`scripts/reset-demo.ps1`). Молча состояние не сбрасывается.

Новый прогон демо — только через `scripts/reset-demo`: он останавливает
сервисы, очищает таблицы прогона (в том числе `matcher_*` и
`stop_events`) и Redis. Без строки в `matcher_cursor` матчер читает поток
с начала. Если при старте поток заканчивается раньше сохранённой позиции,
матчер предупреждает в журнале, что в базе остался прошлый прогон.

Миграция `0004` продолжает цепочку ингеста `0003`.
