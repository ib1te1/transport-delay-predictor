# Сборка системы: ingest, matcher и ML поверх main

Как три открытых PR — #7 (модель в `predictor`), #8 (`ingest`: проигрыватель
CSV и приём NDTP) и #9 (`matcher`) — соединяются с `api` и дашбордом из
`main` в одну систему к сдаче 27 сентября, 23:59 МСК. Общие границы — в
`docs/specs/system-design.md`; здесь только решения по сборке и то, что
в общей спеке из-за них меняется.

## 1. Источники потока для демо

Жюри подаёт поток двумя способами (кейс: «приём и парсинг NDTP от
эмулятора и исторического датасета»).

**Сценарий А — исторический датасет.** Проигрыватель `replay` читает
`/data/<replay.period>/traffic.csv`, сортирует по времени и воспроизводит
с ускорением `replay.speedup`. Выход проигрывателя переключается:

- `sink: ndtp` — основной: каждая строка кодируется в NDTP-кадр по
  таблице «колонка CSV → поле NDTP» из раздачи и уходит по TCP на
  `ingest:9201`; на каждый `unit_id` своя сессия с handshake. Датасет
  проходит тот же парсер, что и эмулятор. `timestamp` — время датасета в
  Unix-секундах (дробная часть теряется). `ingest` принимает такие кадры
  без сдвига времени, `source = emulator_replay`. Подтверждений в NDTP
  нет: курсор проигрывателя двигается по факту отправки, при падении
  возможна потеря последних точек.
- `sink: direct` — запасной, как в #8: запись в `telemetry` и шину
  напрямую. Остаётся по умолчанию, пока `ndtp` не пройдёт сквозной
  прогон.

**Сценарий Б — эмулятор организаторов.** `ingest.mode: emulator`,
эмулятор подключается к `ingest:9201`. Координаты у него случайные
(`autoGenerate`), поэтому сценарий показывает приём протокола,
переподключения и ТС на карте, но не прогнозы. `timestamp` эмулятор
ставит по своим часам, поэтому датасет через него не воспроизводится.

## 2. Период и модель демо

Демо идёт на **validate**: `seed.period = replay.period = validate`,
модель — `models/current`. Ответов validate модель не видела, и ею же
сделан сабмит, поэтому живой MAE на дашборде честный.

На test `current` обучалась (MAE 44.7 против 80.8 у `ctl`, обученной
только на train, — `docs/specs/ml-model.md`), поэтому test для демо не
используется.

## 3. Откуда `cur_dev_s`

Два кандидата:

- `gps` — `predictor` оценивает отклонение по треку из запроса, как
  модель видела его в обучении (так в #7 по умолчанию);
- `request` — берётся `delay_s` последнего `StopEvent` от `matcher`
  (`system-design.md` §2).

Выбор — по замеру: один прогон replay **test** с `matcher`, выгрузка
`stop_events`, затем офлайн на точках test модель `ctl` считается дважды:
с `cur_dev_s` от `matcher` (`hint="given"`) и с `hint="gps"`. Меньший MAE
задаёт `predictor.cur_dev_source`. Этот же прогон — приёмка `matcher` по
`system-design.md` §3.4. Модель `ctl` обязательна: у `current` на test
утечка, она смажет разницу.

Пока замера нет, остаётся `gps`. `matcher` нужен при любом исходе: факты
прибытия дают живой MAE, проверку факта и алерты (`backend-design.md`,
шаг 4) и карточку ТС.

## 4. `matcher` читает шину

`matcher` читает `TelemetryRecord` из шины `telemetry`, а не из таблицы
`ingest`: `XREAD` пачкой от сохранённого id записи. Id хранится в
`matcher_cursor` и меняется в той же транзакции, что состояние и
`stop_events`. Id записей в потоке монотонны, поэтому пропусков строк,
закоммиченных не по порядку, нет, и `matcher` не зависит от схемы
таблиц `ingest`. Миграция `0004` правится на месте, пока #9 не влит.

Смена порогов в `config/assumptions.yaml` при несовпадении с сохранённым
состоянием — ошибка при старте сервиса, а не бесконечный повтор.

## 5. Сброс демо

Состояние прогона лежит в Postgres (`ingest_runs`, `telemetry`,
`matcher_*`, `stop_events`, `predictions`, `alerts`) и в потоках Redis;
`api` при старте перечитывает `stop_events` с начала. Частичный сброс
ломает соседей, поэтому сброс один на всю систему.

- Одноразовый сервис `reset` в профиле compose `reset`, по образцу
  `seed`. Очищает **все** таблицы схемы `public`, кроме списка
  сохраняемых: справочники `seed` (`vehicles`, `stops_plan`) и
  `alembic_version`; `TRUNCATE ... RESTART IDENTITY CASCADE`. Новая
  таблица любого трека очищается без правки `reset`; список меняется
  только с новым справочником `seed`.
- Redis: `FLUSHDB` — в нём только наши потоки.
- `api` и `matcher` держат состояние в памяти, поэтому порядок —
  остановить сервисы, очистить, запустить. Это `scripts/reset-demo.sh` и
  `scripts/reset-demo.ps1`.
- Флаг `--new-run` у проигрывателя убирается; завершённый прогон
  отвечает подсказкой запустить `scripts/reset-demo`.
- Тест: заполнить таблицы, выполнить `reset`, проверить, что пусто всё,
  кроме сохраняемых, а справочники на месте.

## 6. Правки открытых PR

**#8 (`ingest`):**

- кадр с незнакомой ячейкой после `G6CellNav00` не отбрасывается:
  разбор ячеек останавливается, навигация сохраняется;
- темп проигрывателя — от якоря: пауза до
  `start_wall + (event_time − first_event) / speedup`, а не от
  предыдущей строки, чтобы накладные расходы не копились;
- внешняя сортировка выполняется в отдельном потоке до начала
  проигрывания, чтобы SIGTERM обрабатывался сразу;
- `--new-run` убирается (§5).

**#9 (`matcher`):** вход из шины (§4); детектор каждого ТС в памяти,
чекпоинт раз на пачку — если замер покажет, что по одной строке
`matcher` не успевает за ×60; ошибка при старте на смену порогов.

**#7 (ML):** разрешить конфликты с #8 в `config/system.yaml` и
`.github/workflows/ci.yml`; период демо — §2; `LivePredictor` удалить
или перевести `bench` на `Forecaster`, чтобы путь прогноза был один.

## 7. Таймаут `predictor`

Окно запроса из #7 (телеметрия 150 минут, план с начала дня) даёт на test
1.8 МБ и до 555 мс на 13 ТС при `api.predict_timeout_ms = 1000`. Решение
по замеру на прогоне validate: если максимум `/predict` выше ~600 мс,
`predict_timeout_ms` поднимается до 2000 (ориентир кейса — меньше 1–2 с).
Батч на стороне `api` не режется.

`sink: ndtp`, сравнение `cur_dev_s`, инструкция для жюри.
