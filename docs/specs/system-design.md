# Общая архитектура системы

Документ задаёт то, что общее для всех треков: модули и их границы,
контракты между ними, хранилище, время, конфиг, надёжность, сдачу и сроки.
Как устроен каждый модуль внутри, решает его трек в своей спеке в
`docs/specs/`. Исходные условия — в `docs/case-brief.md`.

## 1. Что строим

Систему из трёх модулей, которые жюри проверяет по отдельности и вместе:

- **ML-ядро** — прогноз задержки на целевой остановке и его причина;
- **Бэкенд** — приём потока NDTP, сопоставление с расписанием, оркестрация
  прогнозов, риск, алерты, API;
- **Дашборд** — карта с ТС и риском, карточка инцидента, живые обновления.

Плюс офлайн-сабмит по validate — тем же кодом ML-ядра.

Сквозной путь данных: **поток NDTP → телеметрия → прибытия на остановки →
запрос прогноза → прогноз, риск, алерт → дашборд.**

## 2. Модули и сервисы

```
                         ┌──────────────── Бэкенд ─────────────────┐
эмулятор / проигрыватель │                                         │
      ──NDTP/TCP──►  ingest ──telemetry──► matcher ──stop_events──┐ │
                         │        │                               │ │
                         │        └──────────► api ◄──────────────┘ │
                         │           (оркестрация, риск, алерты,    │
                         │            REST + WS, Swagger)           │
                         └──────────────┬──────────────▲────────────┘
                                 POST /predict     прогноз
                                        ▼              │
                                   ┌─ ML-ядро ─────────┴─┐
                                   │  predictor          │
                                   └─────────────────────┘
          web (дашборд) ◄──── REST + WebSocket ──── api
```

| Сервис | Модуль | Трек | Отвечает за |
| --- | --- | --- | --- |
| `ingest` | Бэкенд | Ингест | TCP-сервер NDTP, разбор кадров, проигрыватель CSV, переподключения. Отдаёт `TelemetryRecord` |
| `matcher` | Бэкенд | Остановки и маршруты | Обнаружение прибытия на остановку, `cur_dev_s` по ТС, маршруты из цепочек остановок |
| `api` | Бэкенд | Бэкенд | Когда и для кого прогнозировать, риск, алерты, REST/WS для дашборда, метрики, Swagger |
| `predictor` | ML-ядро | ML | HTTP-сервис: `PredictRequest` → `PredictResponse`. Обучение и сабмит — его же код, офлайн |
| `web` | Дашборд | Фронтенд | Карта, риск цветом, карточка инцидента, лента алертов |
| `postgres`, `redis` | — | Бэкенд | Хранилище и шина |
| `migrate`, `seed` | — | Бэкенд | Одноразовые задачи: схема, справочники |

Три решения, на которых держатся границы:

- **Когда прогнозировать, решает `api`, а не ML.** Бэкенд выбирает момент
  `T` и целевую остановку по тому же правилу, что в разметке организаторов,
  и отправляет запрос в `predictor`. ML — чистая функция «запрос →
  прогноз», которую одинаково вызывают поток и офлайн-сабмит. Горизонт
  10–15 минут соблюдается по построению: прогноз выдаётся в момент `T`, а
  плановое прибытие — не раньше `T + 10 мин`.
- **Признаки считает ML.** `predictor` получает сырое окно телеметрии и
  контекст расписания, а не готовые признаки. Код признаков один и
  офлайн, и на потоке.
- **`cur_dev_s` на потоке считает `matcher`.** В разметке его дают
  организаторы, в потоке его нет — его приходится вычислять по прибытиям
  на остановки.

## 3. Контракты

Контракты — pydantic-модели в `packages/contracts`. Пакет общий: правка в
нём только после согласования командой, потому что от него зависят все
треки. Всё время в контрактах — **UTC с зоной**; наивное время из CSV
переводится в UTC на входе (`ingest`, `seed`, офлайн-загрузчики ML).

### 3.1. `TelemetryRecord`: `ingest` → шина `telemetry`

Одна запись независимо от источника потока.

```python
class TelemetryRecord(BaseModel):
    tr_id: int | None          # None — unit_id нет в справочнике (ТС без расписания)
    unit_id: int
    event_time: datetime       # время датасета
    lat: float | None
    lon: float | None
    location_valid: bool
    speed_kmh: float | None
    heading_deg: float | None
    source: Literal["replay", "emulator", "emulator_replay"]
```

`event_time` — всегда время датасета. Если поток идёт через эмулятор,
который ставит в пакет текущее время, сдвиг к времени датасета считает
`ingest`; потребители об этом не знают.

### 3.2. `StopEvent`: `matcher` → шина `stop_events`

Одна запись на каждое обнаруженное прибытие.

```python
class StopEvent(BaseModel):
    tr_id: int
    stop_id: int               # tt_action_item_id — плановое прибытие на остановку
    time_plan: datetime
    time_fact: datetime        # обнаруженное прибытие
    delay_s: float             # time_fact − time_plan; это cur_dev_s для следующих прогнозов
```

### 3.3. `PredictRequest` / `PredictResponse`: `api` → `predictor`

`POST /predict`, тело — список запросов, ответ — список ответов в том же
порядке.

```python
class TelemetryPoint(BaseModel):
    event_time: datetime
    lat: float | None
    lon: float | None
    location_valid: bool
    speed_kmh: float | None
    heading_deg: float | None

class ScheduledStop(BaseModel):
    stop_id: int
    time_plan: datetime
    lat: float
    lon: float
    time_fact: datetime | None  # только для остановок, пройденных не позже T

class PredictRequest(BaseModel):
    sample_id: str              # f"{tr_id}_{unix(T)}", как у организаторов
    tr_id: int
    T: datetime
    target_stop_id: int
    target_time_begin: datetime
    cur_dev_s: float | None
    telemetry: list[TelemetryPoint]   # event_time ≤ T
    schedule: list[ScheduledStop]     # остановки ТС вокруг T

class ReasonCode(StrEnum):
    accumulated_delay = "accumulated_delay"
    slow_approach = "slow_approach"
    long_dwell = "long_dwell"
    low_speed_segment = "low_speed_segment"
    stale_telemetry = "stale_telemetry"
    unknown = "unknown"

class PredictResponse(BaseModel):
    sample_id: str
    prediction_s: float         # прогноз задержки на целевой остановке, со знаком
    p_late: float | None        # вероятность опоздания > 120 с, если модель её даёт
    reasons: list[ReasonCode]
    model_version: str
```

Глубина окна телеметрии и диапазон остановок в `schedule` задаются в
конфиге (`api.request`); ML сообщает, сколько ему нужно.

### 3.4. Правила честности прогноза

- **Офлайн ML собирает такой же `PredictRequest` из CSV** и вызывает тот же
  код, что и сервис. Сабмит по validate и поток проходят через одну
  функцию.
- **В запросе нет будущего.** Телеметрия — только `event_time ≤ T`; факт в
  `schedule` — только у остановок, пройденных не позже `T`.
- **Для validate не используются никакие факты из других частей раздачи.**
  Организаторы прямо назвали нечестным получение ответов по validate
  математически из данных, а не прогнозом модели.
- **Приёмка `matcher`:** его `cur_dev_s`, посчитанный при проигрывании
  test-периода, сравнивается с `cur_dev_s` организаторов из
  `labels_test.csv`. Модель учится на цифрах организаторов, на потоке
  получает цифры `matcher`; расхождение между ними — прямая потеря
  точности на потоке.

## 4. Данные и хранилище

**Датасет в репозиторий не попадает.** Раздача распаковывается как есть в
`data/dataset/` (папка в `.gitignore`) и монтируется в контейнеры только
на чтение в `/data`. README для жюри содержит ту же инструкцию.

**Справочники загружает `seed`** — одноразовая задача после `migrate`:
плановое расписание периода демо и соответствие `unit_id` → `tr_id`.
Период задаётся в конфиге. **Факт (`time_fact_begin`) `seed` не загружает
никогда**, даже если он есть в файле.

**Таблицы Postgres** — у каждой один писатель:

| Таблица | Пишет | Содержимое |
| --- | --- | --- |
| `vehicles` | `seed` | `tr_id` ↔ `unit_id` |
| `stops_plan` | `seed` | плановые прибытия: `stop_id`, `tr_id`, `time_plan`, координаты, адрес |
| `telemetry` | `ingest` | `TelemetryRecord` |
| `stop_events` | `matcher` | `StopEvent` |
| `route_shapes` | `matcher` | маршруты: id, упорядоченные остановки, линия для карты |
| `predictions`, `alerts` | `api` | прогнозы и алерты |

Схему своих таблиц трек задаёт в своей спеке и добавляет миграцией в своём
PR. Цепочка alembic одна; CI проверяет, что голова одна.

**Шина — Redis Streams** (`common.bus`): `telemetry`, `stop_events`,
`predictions`.

**Артефакт модели** коммитится в `models/current/`: файл модели и
`meta.json` с `model_version` и списком признаков. `predictor` грузит его
при старте. Жюри поднимает систему без обучения. Предел размера —
~20 МБ; больше — обсуждается отдельно.

## 5. Время

«Сейчас» у системы одно — **время датасета**: максимальный `event_time`
пришедшей телеметрии. Решения «пора прогнозировать» и «данные устарели»
принимаются по этим часам, а не по часам сервера. Поэтому проигрывание с
ускорением не меняет логику. Отдельного сервиса часов нет.

## 6. Конфиг

`config/system.yaml`, по секции на трек: `ingest`, `matcher`, `api`,
`predictor`, `replay`, `seed`. Трек владеет своей секцией. Значение, от
которого зависит поведение, меняется в конфиге, а не в коде. Загрузка и
проверка типов — `common.config`. Исключение — общая секция `dataset`
(например, часовой пояс времени в CSV): её читает любой сервис, владеет
ею бэкенд.

## 7. Надёжность

Ни один сервис не падает от отказа соседа.

| Отказ | Кто замечает | Поведение |
| --- | --- | --- |
| Эмулятор или проигрыватель отключился | `ingest` | Продолжает слушать порт; переподключение и повторный handshake — штатный путь |
| ТС давно не присылает данные | `api` | После `api.stale_after_sec` по часам датасета ТС помечается устаревшим; прогноз строится по последнему состоянию с флагом `degraded` и причиной `stale_telemetry` |
| `predictor` недоступен | `api` | Прогноз = `cur_dev_s` (baseline организаторов), флаг `degraded`; восстановление — само |
| `matcher` отстаёт | `api` | `cur_dev_s = None`; прогноз запрашивается, отсутствие обрабатывает модель |

## 8. Производительность

Утверждения подтверждаются цифрами:

- `api` отдаёт `GET /metrics`: задержка `/predict` (p50/p95), отставание
  обработки от потока, ТС и прогнозов в минуту, упреждение алертов, живой
  MAE;
- скрипт замера прогоняет проигрывание с ускорением и пишет цифры и время
  холодного старта compose в `docs/performance.md`.

## 9. Документация

- Swagger — встроенный в FastAPI, у `api` и у `predictor`.
- Документация по коду — Sphinx с autodoc, собирается одной командой в
  `docs/code/`. У публичных функций и классов во всех треках — docstring.
- `docs/third-party.md` — сторонние материалы и лицензии; новая зависимость
  добавляет строку в том же коммите.

## 11. Что трек описывает в своей спеке

Спека трека — `docs/specs/<трек>-design.md`. Минимум:

- что трек получает и отдаёт — со ссылкой на контракты из §3, без
  пересказа;
- внутреннее устройство и ключевые решения с обоснованием;
- схема своих таблиц, если они есть;
- своя секция конфига;
- как трек проверяет, что работает: тесты и приёмка;
- открытые вопросы и как они закрываются.

Открытые вопросы, известные сейчас:

- **Ингест: источник потока в демо.** Эмулятор в режиме `autoGenerate`
  генерирует случайное движение, не связанное с расписанием; режима
  воспроизведения датасета в его документации нет. Варианты: подавать
  датасет через эмулятор, переотправляя конфиг с координатами из CSV на
  каждом тике, или свой проигрыватель, который шлёт те же NDTP-кадры,
  плюс подключение эмулятора как проверка протокола. Выбор — по
  результату запуска эмулятора; остальных треков он не касается, пока
  соблюдается §3.1.
- **Остановки и маршруты: маршрутов в данных нет** — ни номера, ни
  направления, только `tr_id` и цепочки остановок. Как из них получаются
  `route_shapes`, решает трек.
