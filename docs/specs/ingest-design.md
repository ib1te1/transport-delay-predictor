# Ингест: NDTP и проигрывание телеметрии

Спека трека «Ингест». Общие границы и контракт `TelemetryRecord` заданы в
`docs/specs/system-design.md`; исходные условия — в `docs/case-brief.md`.
Бинарный формат и поведение эмулятора описаны в файле раздачи
`data/dataset/docs/Emulator-and-Telematic-Packets-Specification.md`. Этот
файл не коммитится, поэтому здесь зафиксированы решения, нужные для
реализации и проверки, но не скопирована спецификация протокола целиком.

## 1. Граница трека

`ingest` принимает TCP-поток NDTP от эмулятора, разбирает навигационную
ячейку и публикует `TelemetryRecord` в Redis Stream `telemetry`. Тот же
выходной путь используется проигрывателем `traffic.csv`. Записи хранятся
в таблице `telemetry` для истории и восстановления отправки в шину.

`ingest` не выбирает целевую остановку, не вычисляет отклонение от графика
и не извлекает ML-признаки. Это ответственность `matcher`, `api` и
`predictor` соответственно. Ни факт из `schedule.csv`, ни метки
`labels/*.csv` ингест не читает.

| Вход | Выход |
| --- | --- |
| TCP-кадры NDTP от эмулятора | `TelemetryRecord` в `telemetry` |
| `traffic.csv` выбранного периода | те же записи с `source = "replay"` |
| `vehicles` от `seed` | `tr_id` для известного `unit_id`; иначе `None` |

Оба источника используют один нормализатор и один путь записи. Контракт
из `packages/contracts` не меняется.

## 2. Источник для демо

Рабочий вариант основного воспроизводимого прогона — **прямое
проигрывание CSV** с
`source = "replay"`. Документ эмулятора не описывает чтение CSV: его
`autoGenerate` создаёт случайное движение, не связанное с расписанием, а
`G6CellNav00.timestamp` всегда ставится по часам эмулятора. Поэтому
эмулятор служит отдельной проверкой TCP/NDTP-пути, а точность поточного
прогноза и алерты показываются на данных выбранного периода. Этот выбор
проверяется запуском эмулятора: если он позволит надёжно воспроизвести
датасет без нарушения времени и порядка, решение можно пересмотреть.

Проигрыватель запускается отдельной одноразовой командой после `seed`, а
не автоматически при старте `docker compose up`: повторный запуск compose
не должен незаметно начинать прогон с начала. Он использует тот же образ
и код нормализации, что `ingest`. Период `replay.period` обязан совпадать
с `seed.period`; несовпадение останавливает проигрыватель до первой
публикации. В инструкции для жюри будут две независимые команды: запуск
CSV-прогона и подключение эмулятора к TCP-порту.

Одновременно подавать CSV и эмулятор в одну шину для демонстрации прогнозов
нельзя: независимые часы и несвязанные траектории смешают состояние ТС.
`ingest.mode = replay` отключает TCP-приём телеметрии, а
`ingest.mode = emulator` запрещает запуск CSV-проигрывателя. Переключение
режима между прогонами требует общего сброса демо (`scripts/reset-demo.sh`
или `scripts/reset-demo.ps1`, `docs/specs/integration-design.md` §5); одной
смены конфига недостаточно, поскольку часы `api` не переводятся назад.
Значение `source = "emulator_replay"` в общем контракте зарезервировано;
его можно использовать только после отдельной проверки, что через
эмулятор удаётся воспроизвести CSV с правильной последовательностью.

## 3. TCP-сервер и разбор NDTP

Сервер слушает на отдельном порту `ingest.ndtp.port` внутри контейнера;
HTTP `/health` остаётся на 8000. Для локальной отладки TCP-порт можно
опубликовать на `127.0.0.1`. Эмулятор работает в той же сети compose и
подключается к `ingest:9201`: он сам открывает TCP-соединение, выполняет
handshake и затем отправляет realtime-кадры.
Каждое соединение обрабатывается независимо; закрытие одного сокета не
останавливает слушатель. Повторное подключение начинается с нового
handshake.

TCP не сохраняет границы пакетов. Читатель накапливает ровно 15 байт NPL,
проверяет сигнатуру `0x7E7E`, тип `0x02` и допустимый `dataSize`, затем
дочитывает указанное число байт NPH и тела. При неполном кадре действует
таймаут; при ошибке заголовка соединение закрывается, чтобы не искать
неизвестную границу следующего кадра. CRC-16/Modbus проверяется по NPH и
телу с перестановкой байтов, указанной в документе раздачи. Структуры
little-endian и packed. Кадр с неверной CRC не публикуется.

Первым допустимым кадром соединения должен быть
`NPH_SGC_CONN_REQUEST` (`serviceId = 0`, `type = 100`, версия 6.2).
`peerAddress` в NPL и теле handshake должны совпадать. После него
принимаются `NPH_SND_REALTIME` (`serviceId = 1`, `type = 101`) от того же
`unit_id`; смена адреса требует нового соединения. Ответный handshake
не нужен: по спецификации эмулятор ответы не разбирает.

В realtime-теле первой идёт `G6CellNav00` (`type = 0`, 26 байт): так
эмулятор формирует каждый кадр. Если тело короче заголовка ячейки и
навигации или первая ячейка не навигационная, `parse_realtime` отбрасывает
кадр с причиной `missing_nav`: без времени и координат публиковать нечего.
Соединение при этом продолжает работать.

После навигации остальные ячейки проходятся по размерам из `CELL_SIZES`
(типы 2, 8, 10, 15, 16) только для того, чтобы дойти до конца тела; их
содержимое не используется. Документ эмулятора перечисляет и другие типы
(3–7, 9, 12–14, 17–23: Crown03, Irma04, GSM19, ServerStatistics22 и др.),
размеров которых в декодере нет. На таком типе, на повторной
`G6CellNav00`, на неполном заголовке ячейки или на ячейке, выходящей за
конец тела, разбор останавливается, а уже прочитанная навигация
возвращается и публикуется. Целостность тела к этому моменту проверена
CRC, поэтому сбой в хвосте означает незнакомую или неверно описанную
вспомогательную ячейку, а не порчу навигации. Если отбрасывать такой кадр,
включение в эмуляторе любой из этих ячеек теряет каждый realtime-кадр.

Вместе с навигацией `parse_realtime` возвращает причину остановки
(`unknown_cell`, `short_cell_header`, `short_cell`), тип ячейки и смещение.
`serve_client` считает остановки на сессию по паре (причина, тип): первый
случай пары пишется в лог `WARNING` с `unit_id`, типом и смещением, а при
закрытии соединения непустой счётчик выводится одной строкой `INFO`. Лог
на каждый кадр не пишется: эмулятор шлёт кадр раз в несколько секунд на
терминал, и с включённой ячейкой лог состоял бы из одних предупреждений.
Такой кадр не считается отброшенным.

Кадр отбрасывается целиком при ошибке CRC, флагов NPH, типа сообщения или
навигации; следующий кадр того же соединения может быть принят. Предел
размера кадра и таймаут чтения задаются в конфиге. Для каждого
отброшенного кадра увеличивается счётчик с причиной; содержимое пакета
целиком в лог не пишется.

Тесты. `services/ingest/tests/test_ndtp.py`: навигация, известная ячейка 8,
затем тип 99 и произвольные байты — возвращаются те же поля `Nav`, что без
хвоста, причина `unknown_cell`, тип 99; навигация и обрезанная ячейка 8 —
навигация сохраняется, причина `short_cell`; тело, где ячейка 8 стоит
перед навигацией, — `NdtpError("missing_nav")` без `fatal`. Первый из них
заменяет `test_unknown_auxiliary_cell_is_rejected`.
`services/ingest/tests/test_tcp_server.py`: сессия с кадром, где после
навигации идёт незнакомая ячейка, сохраняет одну запись с координатами
этого кадра.

## 4. Нормализация записи

| Поле контракта | CSV | NDTP |
| --- | --- | --- |
| `unit_id` | колонка `unit_id` | NPL `peerAddress` после handshake |
| `tr_id` | по `vehicles`; колонка CSV служит проверкой соответствия | по `vehicles` |
| `event_time` | `event_time` с зоной `dataset.source_timezone` → UTC | Unix-секунды `G6CellNav00.timestamp` → часы датасета → UTC |
| `lat`, `lon` | колонки CSV | модули координат / `1e7`, знаки из `extraDopBit5/6` |
| `location_valid` | колонка CSV | `extraDopBit7` |
| `speed_kmh`, `heading_deg` | `speed`, `heading` | `speedAvg`, `course` |
| `source` | `replay` | `emulator` |

Если координаты недостоверны, отсутствуют или вне диапазона широты и
долготы, `location_valid = false`, `lat = lon = None`; сама точка остаётся
в потоке и двигает часы датасета. Отсутствующие скорость и курс — `None`.
Широта должна быть в `[-90, 90]`, долгота в `[-180, 180]`, скорость
неотрицательной, курс в `[0, 360]`; все числа конечны. Плохое
необязательное поле становится `None`, плохой `unit_id` или время
приводят к пропуску записи. По каждому виду ошибки ведётся счётчик.

`vehicles` загружается `seed` до старта сервиса. Неизвестный `unit_id`
публикуется с `tr_id = None`: такая запись всё ещё продвигает часы
датасета, но `api` не выбирает для неё прогноз. В CSV при расхождении
`tr_id` строки с соответствием в `vehicles` строка пропускается и ошибка
считается отдельно: нельзя привязать её к чужому расписанию. Для одного
периода справочник не меняется во время прогона.

В NDTP эмулятор ставит текущие Unix-секунды, тогда как расписание живёт
в сутках датасета. Для режима `emulator` при первом корректном пакете
фиксируется сдвиг: его `timestamp` сопоставляется с
`ingest.ndtp.dataset_anchor` из конфига. Сдвиг сохраняется в БД для
текущего прогона и применяется после переподключения и перезапуска
сервиса; разность между следующими пакетами сохраняется. Якорь задаётся
для выбранного периода и не выводится из часов сервера. CSV-режим
сохраняет микросекунды исходного `event_time` и сдвига не применяет.

## 5. Проигрыватель CSV

Файл выбирается как `/data/<replay.period>/traffic.csv`. Он читается
потоком через `csv.DictReader` в UTF-8. До отправки записи **глобально**
упорядочиваются по `(event_time, номер строки)`; равные времена сохраняют
исходный порядок. В локальной раздаче `test/traffic.csv` содержит около
106 тыс. строк и часто возвращается назад по `event_time`, поэтому
публикация в порядке файла нарушила бы общие часы датасета. Значения
`receive_time`, `gps_time`, `is_hist_data`, `packet_id` и данные разметки
не заменяют `event_time` и не попадают в контракт.

### 5.1. Запуск и выбор прогона

Команда `python -m app.replay` (сервис `replay` профиля compose `replay`)
флагов не принимает; лишний аргумент, в том числе прежний `--new-run`,
отклоняется `argparse` с кодом 2. Новый прогон начинается только после
общего сброса демо: `scripts/reset-demo.sh` или `scripts/reset-demo.ps1`
очищает `ingest_runs`, `telemetry` и Redis вместе с состоянием остальных
сервисов. Своя команда «начать заново» у проигрывателя сбрасывала бы
только его часть и оставляла `matcher` и `api` с состоянием прошлого
прогона.

`run_replay` на старте:

1. Загружает конфиг и проверяет файл — до подключения к БД.
2. Удаляет оставшиеся каталоги сортировки (§5.2).
3. `Outbox.drain()` публикует pending-строки, оставшиеся после сбоя.
4. `start_replay_run` под `SELECT ... FOR UPDATE` берёт последний прогон с
   `mode = 'replay'` и действует по таблице ниже.
5. Сортирует файл в отдельном потоке (§5.2), проигрывает его (§5.3) и
   ставит статус `completed`.

| Последний прогон | Действие | Код выхода |
| --- | --- | --- |
| нет | новый прогон `active` с пустым курсором | 0 после завершения |
| `active` или `interrupted`, совпадают `period`, `file_path`, `file_sha256`, `start_at`, `end_at`, `speedup` | resume: статус `active`, курсор из `last_event_time`, `last_line_number` | 0 после завершения |
| `active` или `interrupted`, файл или настройки другие | `ValueError` с подсказкой выполнить `scripts/reset-demo`; ничего не публикуется | 1 |
| `completed` | `ReplayCompleted` из `store.py`; сортировка и публикация не начинаются | 3 |

`active` на старте значит, что прошлый процесс завершился без `finally`
(SIGKILL, падение контейнера); такой прогон возобновляется так же, как
`interrupted`. Ветки режима `new_run` в `start_replay_run` — отказ
«another replay run is active» и проверка pending-строк прошлого прогона —
удаляются: после сброса прошлого прогона в таблице нет.

Для завершённого прогона `main` пишет в лог `WARNING` строку вида
`replay run <run_id> is already completed; to replay again reset the
demo: scripts/reset-demo.sh (or scripts/reset-demo.ps1)` и возвращает 3.
Не 0: проигрывания не было, и `docker compose run --rm replay && …` не
должен принять повторный запуск за выполненный прогон. Не 1: это не сбой,
и CI отличает этот исход от ошибки и от прерывания (130). При запуске через
`docker compose --profile replay up -d replay`, как печатает
`scripts/reset-demo`, подсказка видна в `docker compose logs replay`.

Места, где меняется код и тексты при удалении `--new-run`:

- `services/ingest/app/replay.py`: аргумент `--new-run` в `main`, параметр
  `new_run` у `_run_with_signals`, `run_replay` и `_start`; в `main` —
  обработка `ReplayCompleted` с кодом 3;
- `services/ingest/app/store.py`: параметр `new_run` и связанные с ним
  ветки `start_replay_run`, класс `ReplayCompleted`, подсказка сброса в
  тексте ошибки несовпадения файла или настроек;
- `services/ingest/tests/test_outbox.py`: вызов
  `start_replay_run(..., new_run=True)` заменяется прямой вставкой строки в
  `ingest_runs`: тесту нужен только `run_id`, а без флага
  `start_replay_run` возобновил бы или отверг прогон, оставшийся в общей
  тестовой БД;
- `README.md`: удаляется фраза «Для нового CSV-прогона после такой
  очистки `--new-run` не нужен»; абзац о завершённом прогоне в «Подаче
  телеметрии» ссылается на `scripts/reset-demo` вместо ручной очистки.

`docker-compose.yml`, `config/system.yaml`, `scripts/reset-demo.*` и
`.github/workflows/ci.yml` флаг не упоминают и правки не требуют; в CI
добавляется только проверка повторного запуска.

Тесты. `services/ingest/tests/test_store.py`: завершённый прогон —
`ReplayCompleted`, в `ingest_runs` по-прежнему одна строка; прогон,
оставшийся `active`, возобновляется с тем же `run_id` и курсором.
`services/ingest/tests/test_replay.py`: `main([])` при `_run_with_signals`,
бросающем `ReplayCompleted`, возвращает 3 и пишет в лог `reset-demo`;
`main(["--new-run"])` завершается `SystemExit(2)`. `.github/workflows/ci.yml`,
job `ingest-image`: после проверки строк повторный
`docker compose --profile replay run --rm replay` возвращает 3, а
счётчики `telemetry` и `XLEN telemetry` не меняются.

### 5.2. Сортировка до проигрывания

Внешняя сортировка выполняется целиком до первой публикации, в отдельном
потоке через `asyncio.to_thread`, и пишет результат во временный файл;
цикл событий только читает его. Синхронный генератор в цикле событий
выполнял бы всю сортировку на первой итерации: SIGTERM (`task.cancel`) не
обрабатывался бы до её конца, `docker compose stop` через 10 с посылал бы
SIGKILL, `finally` не выполнялся, и прогон оставался бы `active` вместо
`interrupted`.

`sort.py` вместо генератора `sorted_csv_rows` даёт две функции:
`sort_to_file(path, zone, chunk_rows, out_dir, *, start_at, end_at, after,
stop) -> SortResult` и `read_sorted(path) -> Iterator[SortedCsvRow]`.

- Чтение через `csv.DictReader`, проверка `REQUIRED_COLUMNS` и разбор
  `event_time` — как раньше. Строка без времени не упорядочивается и
  считается в `bad_time`; первые 20 номеров пишутся в лог.
- Фильтр стоит до записи порций. Строка в `[start_at, end_at]` (границы
  включительны) считается в `selected`; в порцию она попадает, только если
  её ключ `(event_time, номер строки)` больше курсора `after`. Сортируется
  и пишется лишь то, что предстоит проиграть, поэтому resume не
  перебирает уже сохранённые строки в цикле событий.
- Порции по `sort_chunk_rows` строк (формат `_write_chunk` без изменений)
  сливаются `heapq.merge` в `sorted.jsonl`, после слияния порции
  удаляются. Единственная неполная порция тоже пишется в `sorted.jsonl`,
  чтобы у проигрывания был один путь.
- `SortResult` содержит путь к `sorted.jsonl` и счётчики `read`,
  `bad_time`, `selected`, `to_play`; проигрыватель переносит их в
  `ReplayStats`. При `selected == 0` запуск завершается прежней ошибкой
  пустого диапазона, до публикации. При `to_play == 0` (процесс упал после
  последней строки, но до `completed`) прогон сразу помечается `completed`.

Временные файлы. `run_replay` создаёт каталог
`tempfile.mkdtemp(prefix="ingest-replay-")` во временном каталоге
контейнера (`/tmp`, слой контейнера; `/data` смонтирован только для
чтения) и удаляет его `shutil.rmtree` в своём `finally` при любом исходе.
Пик занятого места — порции плюс `sorted.jsonl`, около двух размеров
отобранных строк в JSONL. Между запусками файл не переиспользуется: resume
сортирует заново, вне цикла событий это секунды на `test`, и кэш по
`file_sha256` не нужен. Каталоги `ingest-replay-*`, оставшиеся после
SIGKILL, удаляются при старте (шаг 2 в §5.1): при
`docker compose up replay` контейнер и его `/tmp` переживают перезапуск,
а в одном контейнере работает один проигрыватель.

Отмена во время сортировки. Поток получает `threading.Event` `stop`,
проверяет его на каждой прочитанной строке и каждой строке слияния и при
установленном флаге бросает `SortCancelled`. `run_replay` ждёт поток через
`asyncio.shield`: на `CancelledError` ставит `stop`, до 5 с ждёт выхода
потока и пробрасывает отмену. Сам поток отменить нельзя: без флага
сортировка дошла бы до конца, `asyncio.run` при выходе ждёт потоки
исполнителя по умолчанию, контейнер снова получил бы SIGKILL, а
`rmtree` удалял бы каталог, в который ещё пишут. Дальше `finally` ставит
`interrupted` и удаляет каталог, `main` возвращает 130 — в пределах 10 с
`docker compose stop`.

Тесты. `services/ingest/tests/test_sort.py`: `sort_to_file` с
`read_sorted` упорядочивают строки и сохраняют порядок равных времён, как
нынешний тест `sorted_csv_rows`; границы диапазона и курсор отбрасывают
строки, `selected` и `to_play` считаются раздельно; `stop`, выставленный
после второй строки, даёт `SortCancelled`. `services/ingest/tests/test_replay.py`
(Postgres и Redis из CI): `sort_to_file` подменяется функцией, ждущей
`stop`; отмена задачи `run_replay` завершает её `CancelledError` меньше
чем за секунду, `ingest_runs.status = 'interrupted'`, каталогов
`ingest-replay-*` не остаётся.

### 5.3. Темп проигрывания

Темп считается от якоря, а не от предыдущей строки. Якорь — пара
`(anchor_wall, anchor_event)`: монотонное время (`clock`, по умолчанию
`time.monotonic`, подменяется в тестах вместе со `sleep`) и `event_time`
первой строки, опубликованной этим процессом. Эта строка уходит сразу;
перед каждой следующей публикацией

```
delay = anchor_wall + (event_time − anchor_event) / speedup − clock()
```

и при `delay > 0` выполняется `sleep(delay)`. Пропущенная невалидная
строка не ждёт и якорь не задаёт. Ускорение меняет только паузы, но не
`event_time` записи.

Пауза от предыдущей строки не учитывает время обработки. На строку
приходятся `save` (INSERT и UPDATE курсора) и `Outbox.wait_for` → `flush`
→ `_pending`, XADD, `_mark`, `_pending`, затем `_published` — пять
транзакций и обращение к Redis подряд. При 5–10 мс на строку 106 тыс.
строк `test` добавляют к ×60 10–17 минут, и часы датасета в `api`
отстают. От якоря время обработки входит в паузу и не копится: пока
средняя пропускная способность выше номинального темпа строк, каждая
строка публикуется с постоянным опозданием на время своей обработки.

Отставание. При `delay ≤ 0` строка обрабатывается сразу. Отдельной логики
догона нет, и якорь внутри процесса не переносится: после задержки
(ожидание Redis в `wait_for`, медленный Postgres) проигрыватель идёт без
пауз со скоростью обработки, пока не вернётся к графику, и часы `api`
возвращаются к расчётным. Перенос якоря сохранил бы отставание до конца
прогона. Раз в 60 с при отставании больше 1 с пишется
`replay lag_sec=…`: по этой строке на замере видно, успевает ли
проигрыватель.

Resume. Якорь не хранится в БД: новый процесс задаёт его заново по первой
строке, опубликованной после курсора. Простой между процессами — не часть
прогона: от старого якоря проигрыватель отыгрывал бы без пауз всё время
остановки, например ночь.

Пакетная публикация не входит в правку. Подтверждение каждой строки не
нужно для корректности: курсор двигается в `save_telemetry` в одной
транзакции с INSERT, то есть по сохранению, а не по публикации; resume
корректен за счёт `Outbox.drain()` перед `start_replay_run`;
`pending_telemetry` отдаёт строки `ORDER BY id`, а единственный
проигрыватель вставляет их в отсортированном порядке, поэтому порядок в
шине не зависит от размера пачки. Поштучное `wait_for` даёт другое:
строка попадает в шину в свой момент по графику, а при отказе Redis
проигрыватель стоит, а не копит pending-строки (§6). Пачки подняли бы
только пропускную способность, а с якорем время обработки уже не копится.

Тесты. `services/ingest/tests/test_replay.py`: `sleep(d)` двигает
подменённые часы на `d`, `save` — на 0.3 с. Точки через 1 с при
`speedup = 1` публикуются в моменты `t0`, `t0 + 1`, `t0 + 2`, паузы по
0.7 с, прогон кончается в `t0 + 2.3`, а не в `t0 + 2 + 3 · 0.3`. Сохранение
дороже шага (2 с при шаге 1 с): `sleep` не вызывается, отрицательных пауз
нет; после одного дорогого сохранения следующие дешёвые идут без пауз,
пока момент публикации не вернётся к графику. Resume с курсором: первая
строка после курсора уходит без паузы, следующие считаются от неё.
`test_replay_paces_sorted_points_without_changing_dataset_time` с
ожиданием `delays == [0.5, 0.5]` остаётся верным при нулевой стоимости
`save`.

### 5.4. Ошибки, остановка и resume

Невалидная строка пропускается с номером и причиной и двигает курсор
через `advance_replay_cursor`; после прогона выводятся число прочитанных,
опубликованных и пропущенных строк. Если файла нет или заголовок не
содержит обязательных колонок, запуск завершается ошибкой до публикации.
SIGTERM на любом шаге — ожидание outbox, сортировка, пауза, сохранение —
отменяет задачу; если прогон уже выбран, `finally` ставит ему
`interrupted`, затем закрывает соединения. При возобновлении того же
прогона проигрыватель продолжает после последнего сохранённого ключа `(event_time, номер строки)` в
отсортированном порядке и не переводит часы датасета назад. Перед
продолжением он отправляет оставшиеся строки outbox.

## 6. Сохранение и доставка

Запись сначала коммитится в Postgres, затем публикуется в Redis Stream
`telemetry` через `common.bus`. Таблица служит также простым outbox:
неопубликованные строки повторно отправляются после восстановления Redis
или перезапуска ingest. TCP-сервер продолжает принимать подключения при
отказе Redis, пока Postgres доступен. При отказе Postgres приём кадра
прекращается с ошибкой соединения; эмулятор переподключится и повторит
handshake. Проигрыватель ждёт восстановления зависимостей и не
продвигает сохранённый прогресс.

Между успешным `XADD` и отметкой строки как опубликованной возможен
сбой. Тогда повторная отправка даст дубль в шине: для строки, уже
сохранённой в Postgres, гарантия доставки в Redis — **как минимум один
раз**, не ровно один раз. Потерянный до записи в Postgres TCP-кадр
эмулятор не обязан повторять. Повторная публикация не
создаёт вторую строку в Postgres. `matcher` и `api` должны переживать
повтор телеметрии; проверка этого — часть сквозной приёмки с их треками.
Redis Stream ограничен общей длиной из `common.bus`; Postgres остаётся
историей, которую можно использовать для повторной публикации при потере
шины.

## 7. Схема БД

Миграция ингеста добавляет таблицу `telemetry` после текущей единственной
головы Alembic. На один нормализованный вход — одна строка:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `bigserial primary key` | порядок outbox |
| `run_id` | `uuid not null` | один прогон источника, сохраняемый при resume |
| `source_key` | `text not null` | номер CSV-строки либо ID пакета в TCP-сессии |
| `tr_id` | `bigint null` | соответствие из `vehicles` |
| `unit_id` | `bigint not null` | бортовой терминал |
| `event_time` | `timestamptz not null` | часы датасета, UTC |
| `lat`, `lon` | `double precision null` | координаты |
| `location_valid` | `boolean not null` | достоверность координат |
| `speed_kmh`, `heading_deg` | `double precision null` | скорость и курс |
| `source` | `text not null` | значение из `TelemetryRecord.source` |
| `created_at` | `timestamptz not null` | время записи для оценки возраста outbox |
| `published_at` | `timestamptz null` | `NULL` до успешного `XADD` |
| `stream_id` | `text null` | ID Redis Stream для диагностики |

`UNIQUE (run_id, source_key)` делает повтор чтения входа идемпотентным.
Индекс `(tr_id, event_time DESC)` нужен для истории и отладки.
Для CSV `source_key` — физический номер строки файла; для NDTP — номер
кадра вместе со случайным ID конкретной TCP-сессии. Отдельная таблица
`ingest_runs` хранит `run_id uuid primary key`, `mode text not null`,
`period text not null`, `status text not null` (`active`, `completed`,
`interrupted`) и `started_at timestamptz not null`. Для CSV в ней есть
`file_path text`, `file_sha256 text`, `start_at timestamptz`,
`end_at timestamptz`, `speedup double precision`,
`last_event_time timestamptz`, `last_line_number bigint`. Для эмулятора
есть `dataset_anchor timestamptz` и `timestamp_shift_s double precision`.
Неиспользуемые для режима столбцы остаются `NULL`.
Resume разрешён только для того же файла и настроек диапазона (§5.1).
Новый прогон появляется только после общего сброса демо, который очищает
`ingest_runs` и `telemetry`, поэтому два запуска не смешиваются.

## 8. Конфиг и запуск

Параметры поведения находятся в `config/system.yaml`, в секциях
`ingest`, `replay` и общей `dataset`:

```yaml
ingest:
  mode: replay          # replay | emulator
  ndtp:
    host: 0.0.0.0
    port: 9201
    read_timeout_sec: 10
    max_frame_bytes: 65535
    dataset_anchor: null  # обязателен только для режима emulator

replay:
  period: test           # train | test | validate; совпадает с seed.period
  speedup: 60
  start_at: null         # UTC или время в dataset.source_timezone
  end_at: null
  sort_chunk_rows: 20000
```

Неверный порт, неположительный timeout/ускорение, обратный диапазон и
отсутствующий якорь в режиме эмулятора отклоняются при запуске.
`dataset.source_timezone` уже задан общим конфигом. В режиме `emulator`
постоянно работающий `ingest` слушает NDTP; в режиме `replay` одноразовый
проигрыватель читает CSV, а HTTP `/health` остаётся доступным. Команда
проигрывателя флагов не принимает (§5.1); новых параметров конфига правки
§3 и §5 не добавляют. Образ
эмулятора из раздачи подключается как необязательный профиль compose с
адресом `targetHost: ingest`, `targetPort: 9201`; его REST-порт 18080
публикуется на `127.0.0.1` для загрузки конфига.

## 9. Проверка и приёмка

- Unit-тесты декодера: фрагментированный TCP-кадр, несколько кадров за
  одно чтение, CRC, неверный размер, handshake, смена `peerAddress`,
  знаки координат, недостоверная навигация, незнакомая ячейка после
  навигации (навигация сохраняется) и кадр без ведущей навигации (§3).
- Тест нормализации: CSV и эквивалентный NDTP дают одинаковые поля
  телеметрии, кроме неизбежной точности времени и `source`; наивное
  время переводится из `dataset.source_timezone` в UTC.
- Тест проигрывателя: вход не по порядку превращается в монотонный поток;
  одинаковые времена стабильны; ускорение не меняет `event_time`; темп
  от якоря не накапливает время обработки (§5.3); SIGTERM во время
  сортировки оставляет прогон `interrupted` без временных файлов (§5.2);
  остановка и resume не начинают файл заново; завершённый прогон не
  перезапускается и возвращает код 3 (§5.1).
- Интеграционный тест с Postgres и Redis: запись в таблицу предшествует
  публикации, отказ Redis оставляет pending-строку, повтор не создаёт
  вторую строку в БД; неизвестный `unit_id` публикуется с `tr_id = None`.
- Проверка реальным эмулятором из раздачи: несколько `unitId`, handshake,
  realtime-пакеты, отключение и reconnect; после этого в `telemetry`
  появляются валидные записи без перезапуска сервиса.
- Сквозной прогон `test` при одинаковом периоде у `seed` и `replay`:
  `event_time` в шине не убывает, `matcher` видит телеметрию, `api`
  строит прогнозы по часам датасета. Измеряются скорость обработки,
  размер очереди outbox и отставание публикации.

Перед готовностью трека запускаются `ruff check`, `ruff format --check`
и `pytest` из `services/ingest`; CI использует сервисные Postgres и Redis.

## 10. Открытые вопросы

- Проверить реальные кадры из образа эмулятора, особенно CRC и размеры
  дополнительных ячеек, тестом совместимости до фиксации декодера.
- Согласовать с треком `matcher` обработку возможных дублей в Redis
  после сбоя между `XADD` и отметкой outbox.
- После запуска образа эмулятора окончательно подтвердить выбор
  CSV-прогона либо описать проверенный путь `emulator_replay`; до этого
  `emulator_replay` не считается готовым режимом.
- Два процесса проигрывателя одновременно (например, два
  `docker compose run replay`) возобновят один прогон: статус `active` не
  отличает живой процесс от убитого. Строки в `telemetry` не задвоятся
  (`ON CONFLICT`), но курсор может откатиться, а обе копии `Outbox`
  опубликуют одни pending-строки — дубли в шине. Закрывается сессионной
  advisory-блокировкой Postgres на время прогона; в текущие правки не
  входит.
- §3 обещает счётчик отброшенных кадров, а `serve_client` пишет `WARNING`
  на каждый отброшенный кадр без счётчика; поток плохих кадров забивает
  лог.
- Если на замере validate лог `replay lag_sec` покажет устойчивое
  отставание, сократить обращения к БД на строку: `flush` возвращает
  опубликованные id вместо отдельного `_published`, затем — пакетная
  публикация с ограничением числа pending-строк.
