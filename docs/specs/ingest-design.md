# Ингест: NDTP и проигрывание телеметрии

Спека трека «Ингест». Общие границы и контракт `TelemetryRecord` заданы в
`docs/specs/system-design.md`; исходные условия — в `docs/case-brief.md`.
Бинарный формат и поведение эмулятора описаны в файле раздачи
`data/dataset/docs/Emulator-and-Telematic-Packets-Specification.md`. Этот
файл не коммитится, поэтому здесь зафиксированы решения, нужные для
реализации и проверки, но не скопирована спецификация протокола целиком.

## 1. Граница трека

`ingest` принимает TCP-поток NDTP от эмулятора, разбирает навигационную
ячейку и публикует `TelemetryRecord` в Redis Stream `telemetry`. Тот же
выходной путь используется проигрывателем `traffic.csv`. Записи хранятся
в таблице `telemetry` для истории и восстановления отправки в шину.

`ingest` не выбирает целевую остановку, не вычисляет отклонение от графика
и не извлекает ML-признаки. Это ответственность `matcher`, `api` и
`predictor` соответственно. Ни факт из `schedule.csv`, ни метки
`labels/*.csv` ингест не читает.

| Вход | Выход |
| --- | --- |
| TCP-кадры NDTP от эмулятора | `TelemetryRecord` в `telemetry` |
| `traffic.csv` выбранного периода | те же записи с `source = "replay"` |
| `vehicles` от `seed` | `tr_id` для известного `unit_id`; иначе `None` |

Оба источника используют один нормализатор и один путь записи. Контракт
из `packages/contracts` не меняется.

## 2. Источник для демо

Рабочий вариант основного воспроизводимого прогона — **прямое
проигрывание CSV** с
`source = "replay"`. Документ эмулятора не описывает чтение CSV: его
`autoGenerate` создаёт случайное движение, не связанное с расписанием, а
`G6CellNav00.timestamp` всегда ставится по часам эмулятора. Поэтому
эмулятор служит отдельной проверкой TCP/NDTP-пути, а точность поточного
прогноза и алерты показываются на данных выбранного периода. Этот выбор
проверяется запуском эмулятора: если он позволит надёжно воспроизвести
датасет без нарушения времени и порядка, решение можно пересмотреть.

Проигрыватель запускается отдельной одноразовой командой после `seed`, а
не автоматически при старте `docker compose up`: повторный запуск compose
не должен незаметно начинать прогон с начала. Он использует тот же образ
и код нормализации, что `ingest`. Период `replay.period` обязан совпадать
с `seed.period`; несовпадение останавливает проигрыватель до первой
публикации. В инструкции для жюри будут две независимые команды: запуск
CSV-прогона и подключение эмулятора к TCP-порту.

Одновременно подавать CSV и эмулятор в одну шину для демонстрации прогнозов
нельзя: независимые часы и несвязанные траектории смешают состояние ТС.
`ingest.mode = replay` отключает TCP-приём телеметрии, а
`ingest.mode = emulator` запрещает запуск CSV-проигрывателя. Переключение
режима между прогонами требует очистки состояния демо в Redis и таблиц
производных событий по общей инструкции запуска; одной смены конфига
недостаточно, поскольку часы `api` не переводятся назад.
Значение `source = "emulator_replay"` в общем контракте зарезервировано;
его можно использовать только после отдельной проверки, что через
эмулятор удаётся воспроизвести CSV с правильной последовательностью.

## 3. TCP-сервер и разбор NDTP

Сервер слушает на отдельном порту `ingest.ndtp.port` внутри контейнера;
HTTP `/health` остаётся на 8000. Для локальной отладки TCP-порт можно
опубликовать на `127.0.0.1`. Эмулятор работает в той же сети compose и
подключается к `ingest:9201`: он сам открывает TCP-соединение, выполняет
handshake и затем отправляет realtime-кадры.
Каждое соединение обрабатывается независимо; закрытие одного сокета не
останавливает слушатель. Повторное подключение начинается с нового
handshake.

TCP не сохраняет границы пакетов. Читатель накапливает ровно 15 байт NPL,
проверяет сигнатуру `0x7E7E`, тип `0x02` и допустимый `dataSize`, затем
дочитывает указанное число байт NPH и тела. При неполном кадре действует
таймаут; при ошибке заголовка соединение закрывается, чтобы не искать
неизвестную границу следующего кадра. CRC-16/Modbus проверяется по NPH и
телу с перестановкой байтов, указанной в документе раздачи. Структуры
little-endian и packed. Кадр с неверной CRC не публикуется.

Первым допустимым кадром соединения должен быть
`NPH_SGC_CONN_REQUEST` (`serviceId = 0`, `type = 100`, версия 6.2).
`peerAddress` в NPL и теле handshake должны совпадать. После него
принимаются `NPH_SND_REALTIME` (`serviceId = 1`, `type = 101`) от того же
`unit_id`; смена адреса требует нового соединения. Ответный handshake
не нужен: по спецификации эмулятор ответы не разбирает.

В realtime-теле разбирается первая `G6CellNav00` (`type = 0`, 26 байт).
Остальные ячейки пропускаются по известным размерам из документа NDTP;
для неизвестного типа или обрезанной ячейки отбрасывается весь кадр, но
следующий кадр того же соединения может быть принят. Предел размера кадра
и таймаут чтения задаются в конфиге. Для каждого отброшенного кадра
увеличивается счётчик с причиной; содержимое пакета целиком в лог не
пишется.

## 4. Нормализация записи

| Поле контракта | CSV | NDTP |
| --- | --- | --- |
| `unit_id` | колонка `unit_id` | NPL `peerAddress` после handshake |
| `tr_id` | по `vehicles`; колонка CSV служит проверкой соответствия | по `vehicles` |
| `event_time` | `event_time` с зоной `dataset.source_timezone` → UTC | Unix-секунды `G6CellNav00.timestamp` → часы датасета → UTC |
| `lat`, `lon` | колонки CSV | модули координат / `1e7`, знаки из `extraDopBit5/6` |
| `location_valid` | колонка CSV | `extraDopBit7` |
| `speed_kmh`, `heading_deg` | `speed`, `heading` | `speedAvg`, `course` |
| `source` | `replay` | `emulator` |

Если координаты недостоверны, отсутствуют или вне диапазона широты и
долготы, `location_valid = false`, `lat = lon = None`; сама точка остаётся
в потоке и двигает часы датасета. Отсутствующие скорость и курс — `None`.
Широта должна быть в `[-90, 90]`, долгота в `[-180, 180]`, скорость
неотрицательной, курс в `[0, 360]`; все числа конечны. Плохое
необязательное поле становится `None`, плохой `unit_id` или время
приводят к пропуску записи. По каждому виду ошибки ведётся счётчик.

`vehicles` загружается `seed` до старта сервиса. Неизвестный `unit_id`
публикуется с `tr_id = None`: такая запись всё ещё продвигает часы
датасета, но `api` не выбирает для неё прогноз. В CSV при расхождении
`tr_id` строки с соответствием в `vehicles` строка пропускается и ошибка
считается отдельно: нельзя привязать её к чужому расписанию. Для одного
периода справочник не меняется во время прогона.

В NDTP эмулятор ставит текущие Unix-секунды, тогда как расписание живёт
в сутках датасета. Для режима `emulator` при первом корректном пакете
фиксируется сдвиг: его `timestamp` сопоставляется с
`ingest.ndtp.dataset_anchor` из конфига. Сдвиг сохраняется в БД для
текущего прогона и применяется после переподключения и перезапуска
сервиса; разность между следующими пакетами сохраняется. Якорь задаётся
для выбранного периода и не выводится из часов сервера. CSV-режим
сохраняет микросекунды исходного `event_time` и сдвига не применяет.

## 5. Проигрыватель CSV

Файл выбирается как `/data/<replay.period>/traffic.csv`. Он читается
потоком через `csv.DictReader` в UTF-8. До отправки записи **глобально**
упорядочиваются по `(event_time, номер строки)`; равные времена сохраняют
исходный порядок. В локальной раздаче `test/traffic.csv` содержит около
106 тыс. строк и часто возвращается назад по `event_time`, поэтому
публикация в порядке файла нарушила бы общие часы датасета. Сортировка
реализуется порциями через временные файлы и слияние, чтобы не держать
весь `train` в памяти. Временные файлы не попадают в репозиторий.

Первая точка выбранного диапазона отправляется сразу. Для следующих
точек пауза равна разности соседних `event_time`, делённой на
`replay.speedup`; отрицательных пауз после сортировки нет. Границы
`replay.start_at` и `replay.end_at` включительны и применяются до
публикации; пустой диапазон завершается с понятной ошибкой. Ускорение
меняет только реальные паузы, но не `event_time` записи. Значения
`receive_time`, `gps_time`, `is_hist_data`, `packet_id` и данные разметки
не заменяют `event_time` и не попадают в контракт.

Невалидная строка пропускается с номером и причиной; после прогона
выводятся число прочитанных, опубликованных и пропущенных строк. Если
файла нет или заголовок не содержит обязательных колонок, запуск
завершается ошибкой до публикации. Остановка по SIGTERM закрывает
соединения и сохраняет прогресс. При возобновлении того же прогона
проигрыватель продолжает после последнего подтверждённого ключа
`(event_time, номер строки)` в отсортированном порядке и не переводит
часы датасета назад. Перед продолжением он отправляет оставшиеся строки
outbox того же прогона.

## 6. Сохранение и доставка

Запись сначала коммитится в Postgres, затем публикуется в Redis Stream
`telemetry` через `common.bus`. Таблица служит также простым outbox:
неопубликованные строки повторно отправляются после восстановления Redis
или перезапуска ingest. TCP-сервер продолжает принимать подключения при
отказе Redis, пока Postgres доступен. При отказе Postgres приём кадра
прекращается с ошибкой соединения; эмулятор переподключится и повторит
handshake. Проигрыватель ждёт восстановления зависимостей и не
продвигает сохранённый прогресс.

Между успешным `XADD` и отметкой строки как опубликованной возможен
сбой. Тогда повторная отправка даст дубль в шине: для строки, уже
сохранённой в Postgres, гарантия доставки в Redis — **как минимум один
раз**, не ровно один раз. Потерянный до записи в Postgres TCP-кадр
эмулятор не обязан повторять. Повторная публикация не
создаёт вторую строку в Postgres. `matcher` и `api` должны переживать
повтор телеметрии; проверка этого — часть сквозной приёмки с их треками.
Redis Stream ограничен общей длиной из `common.bus`; Postgres остаётся
историей, которую можно использовать для повторной публикации при потере
шины.

## 7. Схема БД

Миграция ингеста добавляет таблицу `telemetry` после текущей единственной
головы Alembic. На один нормализованный вход — одна строка:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `bigserial primary key` | порядок outbox |
| `run_id` | `uuid not null` | один прогон источника, сохраняемый при resume |
| `source_key` | `text not null` | номер CSV-строки либо ID пакета в TCP-сессии |
| `tr_id` | `bigint null` | соответствие из `vehicles` |
| `unit_id` | `bigint not null` | бортовой терминал |
| `event_time` | `timestamptz not null` | часы датасета, UTC |
| `lat`, `lon` | `double precision null` | координаты |
| `location_valid` | `boolean not null` | достоверность координат |
| `speed_kmh`, `heading_deg` | `double precision null` | скорость и курс |
| `source` | `text not null` | значение из `TelemetryRecord.source` |
| `published_at` | `timestamptz null` | `NULL` до успешного `XADD` |
| `stream_id` | `text null` | ID Redis Stream для диагностики |

`UNIQUE (run_id, source_key)` делает повтор чтения входа идемпотентным.
Индекс `(tr_id, event_time DESC)` нужен для истории и отладки.
Для CSV `source_key` — физический номер строки файла; для NDTP — номер
кадра вместе со случайным ID конкретной TCP-сессии. Отдельная таблица
`ingest_runs` хранит `run_id uuid primary key`, `mode text not null`,
`period text not null`, `status text not null` (`active`, `completed`,
`interrupted`) и `started_at timestamptz not null`. Для CSV в ней есть
`file_path text`, `file_sha256 text`, `start_at timestamptz`,
`end_at timestamptz`, `speedup double precision`,
`last_event_time timestamptz`, `last_line_number bigint`. Для эмулятора
есть `dataset_anchor timestamptz` и `timestamp_shift_s double precision`.
Неиспользуемые для режима столбцы остаются `NULL`.
Resume разрешён только для того же файла и настроек диапазона; новый
прогон создаётся явной командой после отправки всех pending-строк
предыдущего, чтобы не смешать два запуска.

## 8. Конфиг и запуск

Параметры поведения находятся в `config/system.yaml`, в секциях
`ingest`, `replay` и общей `dataset`:

```yaml
ingest:
  mode: replay          # replay | emulator
  ndtp:
    host: 0.0.0.0
    port: 9201
    read_timeout_sec: 10
    max_frame_bytes: 65535
    dataset_anchor: null  # обязателен только для режима emulator

replay:
  period: test           # train | test | validate; совпадает с seed.period
  speedup: 60
  start_at: null         # UTC или время в dataset.source_timezone
  end_at: null
  sort_chunk_rows: 20000
```

Неверный порт, неположительный timeout/ускорение, обратный диапазон и
отсутствующий якорь в режиме эмулятора отклоняются при запуске.
`dataset.source_timezone` уже задан общим конфигом. В режиме `emulator`
постоянно работающий `ingest` слушает NDTP; в режиме `replay` одноразовый
проигрыватель читает CSV, а HTTP `/health` остаётся доступным. Образ
эмулятора из раздачи подключается как необязательный профиль compose с
адресом `targetHost: ingest`, `targetPort: 9201`; его REST-порт 18080
публикуется на `127.0.0.1` для загрузки конфига.

## 9. Проверка и приёмка

- Unit-тесты декодера: фрагментированный TCP-кадр, несколько кадров за
  одно чтение, CRC, неверный размер, handshake, смена `peerAddress`,
  знаки координат, недостоверная навигация и неизвестная ячейка.
- Тест нормализации: CSV и эквивалентный NDTP дают одинаковые поля
  телеметрии, кроме неизбежной точности времени и `source`; наивное
  время переводится из `dataset.source_timezone` в UTC.
- Тест проигрывателя: вход не по порядку превращается в монотонный поток;
  одинаковые времена стабильны; ускорение не меняет `event_time`;
  остановка и resume не начинают файл заново.
- Интеграционный тест с Postgres и Redis: запись в таблицу предшествует
  публикации, отказ Redis оставляет pending-строку, повтор не создаёт
  вторую строку в БД; неизвестный `unit_id` публикуется с `tr_id = None`.
- Проверка реальным эмулятором из раздачи: несколько `unitId`, handshake,
  realtime-пакеты, отключение и reconnect; после этого в `telemetry`
  появляются валидные записи без перезапуска сервиса.
- Сквозной прогон `test` при одинаковом периоде у `seed` и `replay`:
  `event_time` в шине не убывает, `matcher` видит телеметрию, `api`
  строит прогнозы по часам датасета. Измеряются скорость обработки,
  размер очереди outbox и отставание публикации.

Перед готовностью трека запускаются `ruff check`, `ruff format --check`
и `pytest` из `services/ingest`; CI использует сервисные Postgres и Redis.

## 10. Открытые вопросы

- Проверить реальные кадры из образа эмулятора, особенно CRC и размеры
  дополнительных ячеек, тестом совместимости до фиксации декодера.
- Согласовать с треком `matcher` обработку возможных дублей в Redis
  после сбоя между `XADD` и отметкой outbox.
- После запуска образа эмулятора окончательно подтвердить выбор
  CSV-прогона либо описать проверенный путь `emulator_replay`; до этого
  `emulator_replay` не считается готовым режимом.
