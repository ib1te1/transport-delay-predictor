# Бэкенд: оркестрация, API, инфраструктура

Спека трека «Бэкенд». Общие границы и контракты — в
`docs/specs/system-design.md`; здесь они не пересказываются, а
используются.

## 1. Зона ответственности

- сервис `api`: оркестрация прогнозов, риск, алерты, REST и WebSocket для
  дашборда, метрики, Swagger;
- `seed`: загрузка справочников;
- инфраструктура: compose, миграции, `packages/common`, CI;
- заглушка `predictor`, пока ML не заменил её моделью;
- сборка документации, README и инструкция для жюри,
  `docs/performance.md`.

## 2. Состояние `api`

`api` читает две шины и держит свежее состояние в памяти:

- из `telemetry` — **часы датасета** (максимальный `event_time`) и по
  каждому ТС окно телеметрии за `api.request.telemetry_window_sec` по
  часам датасета; последняя запись окна — текущая позиция;
- из `stop_events` — по каждому ТС все пройденные остановки из шины
  (их порядка 5,5 тыс. в сутки); в запрос идут только те, что попали в
  окно расписания, а `delay_s` последней из них — актуальный `cur_dev_s`.

Кроме шин, `api` держит последний прогноз каждого ТС — из него
дашборд получает текущий прогноз (§7.1).

Таблицы `telemetry` и `stop_events` `api` не читает. Они принадлежат
`ingest` и `matcher`, их схемы описаны в спеках этих треков и нужны для
истории, отладки и обучения; цикл прогноза от них не зависит. Шины `api`
читает и так — ради позиций и часов, а объём в памяти мал: порядка
десятков ТС по паре сотен точек.

**После перезапуска `api`** состояние восстанавливается из тех же шин:

- телеметрия — чтением `telemetry` с конца (`XREVRANGE`), пока
  `event_time` не станет старше `часы − telemetry_window_sec`;
- пройденные остановки — чтением `stop_events` целиком: это порядка
  5,5 тыс. записей в сутки, до обрезки шины по длине далеко;
- последние прогнозы — из таблицы `predictions`, по одному на ТС, с `t`
  не старше `часы − telemetry_window_sec`;
- открытые алерты — из таблицы `alerts`.

Если перезапустился Redis (в compose он без тома), шины пусты и окно
заполняется заново за `telemetry_window_sec`. До тех пор прогнозы
строятся по неполному окну и помечаются как прогрев (§3); для
демонстрации это приемлемо.

Состояние в памяти — кэш, а не источник правды.

## 3. Цикл прогноза

Раз в `api.scoring_period_sec` **по часам датасета** для каждого
активного ТС (есть `tr_id`, последняя запись не старше
`api.drop_after_sec`).

Тик наступает, когда часы ушли от `T` прошлого тика не меньше чем на
период; первый — как только часы известны. `T` тика — текущие часы, а не
граница периода. Если при ускоренном проигрывании часы за время одного
тика прошли несколько периодов, пропущенные тики не догоняются: прогноз
на прошлое никому не нужен, а догонялка отставала бы от потока всё
сильнее. Часы проверяются несколько раз в секунду реального времени.

На обычной скорости пропусков нет: тик короче периода. При сильном
ускорении прогнозы идут реже, но каждый — на текущий момент; платим
плотностью истории в `predictions` (меньше выборка живого MAE, алерт
может открыться на период позже). Плотная история для оценки модели
строится офлайн из CSV, а не из потока.

1. `T` — текущее время датасета.
2. **Целевая остановка** — первая плановая остановка этого ТС с
   `time_plan` в `(T + 10 мин, T + 15 мин]`: левая граница не входит,
   правая входит. Если такой нет, прогноза в этот тик нет.
3. **Сборка `PredictRequest`:**
   - телеметрия ТС за `[T − api.request.telemetry_window_sec, T]`;
   - остановки ТС с `time_plan` в
     `[T − api.request.schedule_back_sec, target_time_begin]`, факт — только
     из `stop_events` с `time_fact ≤ T`;
   - `cur_dev_s` — `delay_s` последнего `StopEvent` с `time_fact ≤ T`,
     иначе `None`;
   - `sample_id = f"{tr_id}_{int(T.timestamp())}"`.
4. Все запросы тика — **одной пачкой** в `POST /predict` с таймаутом
   `api.predict_timeout_ms`.
5. Ответ пишется в `predictions`, по нему пересчитываются риск и алерты,
   изменения публикуются в шину `predictions` — строкой таблицы целиком —
   и в канал дашборда (§7.3).
   Повторный прогноз с тем же `sample_id` (тик после перезапуска `api`)
   не перезаписывает первый и не публикуется: в шину и на дашборд уходят
   только строки, которые легли в таблицу.

**Если `predictor` не ответил** (ошибка, таймаут, неверный ответ) —
для каждого запроса пачки `prediction_s = cur_dev_s` (или `0`, если
`cur_dev_s` нет), `reasons = [unknown]`, `model_version = "fallback"`,
`degraded = true`, `degraded_reason = "predictor_unavailable"`. Следующий
тик снова пробует `predictor`.

**ТС устарело** (запись старше `api.stale_after_sec`, но не старше
`api.drop_after_sec`) — прогноз строится как обычно по последнему
состоянию, с `degraded = true`, `degraded_reason = "stale_telemetry"` и
причиной `stale_telemetry` в `reasons`. Старше `api.drop_after_sec` — ТС
выводится из цикла и на карте показывается серым.

**Прогрев** — окно телеметрии ещё не накоплено: самая ранняя
телеметрия в памяти `api` новее `T − api.request.telemetry_window_sec`.
Так бывает в начале прогона и после перезапуска Redis. Прогноз строится
как обычно, с `degraded = true` и `degraded_reason = "warming_up"`;
`reasons` не меняются — это свойство входа, а не причина задержки.

Если причин несколько, в `degraded_reason` пишется одна, по старшинству:
`predictor_unavailable`, `stale_telemetry`, `warming_up`.

## 4. Проверка прогнозов по факту

Когда приходит `StopEvent`, всем записям `predictions` с этим
`target_stop_id` проставляются `actual_delay_s = delay_s` и
`abs_error_s = |prediction_s − delay_s|`. Живой MAE — среднее
`abs_error_s` по проверенным прогнозам; отдаётся в `/metrics` и в снимке
для дашборда.

Проверка — в обработчике шины `stop_events`, одно прибытие — один
`UPDATE` по индексу `target_stop_id`. При старте цикла все прибытия из
шины проверяются заново одним запросом: так не теряются те, что пришли,
пока `api` не работал. Строка с тем же фактом не переписывается, поэтому
повторная проверка ничего не меняет.

Живой MAE пересчитывается запросом к таблице после каждого прибытия,
которое изменило строки, и хранится в памяти рядом со снимком: снимок
по-прежнему не обращается к базе. До первой проверки
`live_mae_s = null`, `checked_predictions = 0`.

Не проверяется прогноз, записанный уже после прибытия на свою цель.
Цель лежит в `(T + 10 мин, T + 15 мин]`, так что это опережение больше
чем на 10 минут; в MAE такие прогнозы не попадают.

## 5. Риск

Уровень риска ТС — по `prediction_s` текущего прогноза. Пороги — в
конфиге (`api.risk`), по умолчанию из классов организаторов:

| Уровень | Условие |
| --- | --- |
| `green` | `−60 ≤ prediction_s ≤ 120` |
| `yellow` | `120 < prediction_s ≤ 300` или `prediction_s < −60` |
| `red` | `prediction_s > 300` |

Опережение — жёлтое: ранний уход ломает интервал так же, как опоздание.
`p_late` показывается в карточке, но на цвет не влияет — у ТС один
источник цвета.

**Риск маршрута** — худший уровень среди ТС, чья текущая целевая
остановка лежит на этом маршруте. Маршруты — из `route_shapes`; пока
таблица пуста, `/api/routes` отдаёт пустой список.

## 6. Алерты

- **Открытие.** Прогноз по паре (ТС, целевая остановка) стал `red`, а
  открытого алерта по этой паре нет. Открытый алерт на пару — не больше
  одного; гарантирует уникальный частичный индекс.
- **Обновление.** Новые прогнозы по той же паре обновляют
  `predicted_delay_s` и `reasons`; `opened_at` не меняется.
- **Подтверждение.** Пришёл `StopEvent` по целевой остановке:
  `status = confirmed`, записываются `actual_delay_s` и
  `lead_time_s = time_fact − opened_at`.
- **Отмена.** Прогноз по паре опустился ниже `red`: `status = cancelled`.
  Если по той же паре снова `red` — открывается новый алерт.
- **Отмена после проезда.** Пришёл `StopEvent` того же ТС по остановке,
  запланированной позже целевой, а прибытия на целевую не было:
  `status = cancelled`, `closed_at` — самое раннее такое прибытие,
  `actual_delay_s` и `lead_time_s` пустые. Без этого алерт, чью цель
  `matcher` не распознал, висел бы открытым до конца прогона: следующие
  прогнозы ТС идут по другим целевым остановкам и его не трогают.

Участок алерта — от последней пройденной остановки ТС
(`segment_from_stop_id`) до целевой.

Алерт не бывает задним числом по построению: `opened_at = T`, а плановое
прибытие не раньше `T + 10 мин`. Среднее `lead_time_s` по подтверждённым
алертам — в `/metrics` и на дашборде.

«Подтверждён» значит, что прибытие пришло, а не что опоздание сбылось:
сбылось ли, видно по `actual_delay_s`. `closed_at` — `T` тика у
отменённого алерта и `time_fact` у подтверждённого.

Открытие, обновление и отмена считаются по строкам тика сразу после их
записи, отдельной транзакцией. Подтверждение — в том же обработчике
прибытия, что и проверка прогнозов (§4), в том числе при старте цикла.
Каждое изменение уходит на дашборд сообщением `alert` (§7.3). Открытые
алерты снимок держит в памяти; после перезапуска цикла они загружаются из
таблицы.

Если `matcher` так и не выдал прибытие на целевую остановку, алерт
остаётся открытым: по времени он не закрывается.

## 7. API для дашборда

Схемы — в `services/api/app/schemas.py`; фронт генерирует TS-типы из
`openapi.json`. Схемы WS-сообщений туда тоже попадают: объединение
`WsMessage` с дискриминатором `type` добавляется в `components.schemas`,
хотя ни один эндпоинт его не возвращает.

| Эндпоинт | Ответ |
| --- | --- |
| `GET /health` | живость |
| `GET /api/state` | снимок `StateSnapshot`, §7.1 |
| `GET /api/vehicles/{tr_id}` | карточка `VehicleCard`, §7.2 |
| `GET /api/alerts?status=&limit=` | алерты по статусу (без `status` — все), новые сверху; не больше `limit`, по умолчанию 200, до 1000 |
| `GET /api/routes` | маршруты с линией и уровнем риска |
| `GET /api/stops` | остановки периода для карты |
| `GET /metrics` | см. §9 |

`/api/stops` отдаёт остановки всех запланированных рейсов из `stops_plan`.
`route_id` соответствует `tr_id`, так как в исходном расписании нет номера
маршрута; `stop_order` начинается с 1 внутри рейса и определяется по
`time_plan`, затем по `stop_id`. При отсутствии данных ответ — пустой список,
при недоступности Postgres — `503`. Эти точки позволяют построить линию
последовательности остановок, но не геометрию дорог.

`/api/alerts` и `/metrics` читают базу и отвечают `503`, если Postgres не
ответил.

**Не реализован** на 27.09: `/api/routes` отвечает `404`.

**CORS.** Дашборд открывается с другого origin, чем `api`: браузер
загружает страницу с `web` (`:5173`) и ходит в `api` по `VITE_API_URL`
(`:8000`, `PUBLIC_API_URL`). `api` отдаёт `Access-Control-Allow-Origin`
через `CORSMiddleware` (Starlette/FastAPI). Список разрешённых origin —
`api.cors_origins` в конфиге (список строк), по умолчанию
`["http://localhost:5173", "http://127.0.0.1:5173"]`, поэтому конфиг без
этого ключа тоже работает.
При доступе с других машин (`BIND_ADDR=0.0.0.0`) в `cors_origins`
добавляется внешний адрес дашборда. Разрешён только `GET` (и preflight
`OPTIONS`, его обрабатывает сама middleware); credentials выключены,
wildcard `*` по умолчанию не используется. Прокси Vite для `/api` и
`/ws` в этом решении не используется — дашборд и `api` остаются разными
origin. Без заголовка браузер блокирует REST; WebSocket CORS не
проверяет.

### 7.1. Вид ТС и снимок

`VehicleView` — ТС на карте. Та же форма — в снимке и в WS-сообщении
`vehicles`.

| Поле | Откуда |
| --- | --- |
| `tr_id`, `unit_id` | последняя запись телеметрии ТС |
| `lat`, `lon`, `heading_deg`, `speed_kmh` | последняя запись окна с валидной позицией (`location_valid`, координаты не `null`); нет такой — все четыре `null` |
| `last_seen` | `event_time` последней записи, валидной или нет |
| `freshness` | `active`, если `часы − last_seen ≤ api.stale_after_sec`; `stale`, если `≤ api.drop_after_sec`; иначе `offline` |
| `prediction` | текущий прогноз `PredictionView` или `null` |

`freshness` повторяет пороги цикла (§3): `stale` — ТС ещё в цикле, но
прогноз строится по последнему состоянию; `offline` — ТС вне цикла.

`PredictionView` — прогноз в том виде, в каком его показывает дашборд:
`sample_id`, `t`, `target_stop_id`, `target_address`, `target_time_begin`,
`prediction_s`, `p_late`, `reasons`, `risk_level`, `degraded`,
`degraded_reason`, `model_version`. Адрес берётся из `stops_plan`.

**Текущий прогноз** ТС — последний его прогноз, пока:

- по целевой остановке не пришёл `StopEvent`;
- ТС не `offline`.

Новый прогноз заменяет прежний. После прохода цели прогноза нет до
следующего тика, в котором для ТС найдётся целевая остановка. Время
жизни не привязано к периоду тика: при ускоренном проигрывании тики
пропускаются (§3), и прогнозы мигали бы.

**Цвет ТС** на карте — `prediction.risk_level`; без прогноза ТС
нейтральное, в `offline` — серое. Отдельного уровня риска у ТС нет:
источник цвета один (§5).

ТС пропадает из вида, когда его последняя точка старше окна телеметрии
и `api` его забывает (§2).

`StateSnapshot`:

- `seq` — номер последнего опубликованного WS-сообщения (§7.3);
- `clock` — часы датасета, `null`, пока телеметрии не было;
- `vehicles` — все `VehicleView` по возрастанию `tr_id`;
- `summary` — `risk`: число ТС по `green` / `yellow` / `red` / `none`
  (без текущего прогноза, включая `offline`); `freshness`: по `active` /
  `stale` / `offline`;
- `alerts` — открытые алерты (`AlertView`, поля `AlertRow`), новые
  сверху;
- `live_mae_s`, `checked_predictions` — живой MAE и число проверенных
  прогнозов (§4).

Без открытых алертов `alerts` — пустой список; до первой проверки
прогноза `live_mae_s = null`, `checked_predictions = 0`. Живой MAE по WS
не рассылается: дашборд берёт его из снимка или из `/metrics`.

Пока цикл прогноза не поднял состояние (Postgres не отвечает, шины
пусты), снимок — `seq = 0`, `clock = null`, пустые списки; не `503`:
дашборд показывает ожидание данных, а не ошибку.

### 7.2. Карточка ТС

`VehicleCard`:

- `seq`, `clock` — как в снимке;
- `vehicle` — `VehicleView` или `null`, если ТС есть в плане, но его нет
  в окне телеметрии;
- `predictions` — прогнозы ТС с `t ≥ часы − api.card_track_sec`, новые
  сверху, из таблицы `predictions`;
- `track` — точки с валидной позицией за `api.card_track_sec`:
  `event_time`, `lat`, `lon`, `speed_kmh`;
- `stops` — плановые остановки ТС с `time_plan` в
  `[часы − api.card_track_sec, часы + api.card_track_sec]`: `stop_id`,
  `address`, `lat`, `lon`, `time_plan`, а если по остановке пришёл
  `StopEvent` — `time_fact` и `delay_s`, иначе `null`.

`404` — `tr_id` нет ни в плане, ни в окне телеметрии. `503` — цикл ещё
не поднял состояние (нельзя сказать, есть ли такое ТС) или Postgres не
ответил.

### 7.3. WebSocket `/ws`

Только изменения; состояние целиком — из снимка. Конверт —
`{type, data}` (`common.bus.BusMessage`); `seq` лежит в `data`. Счётчик
`seq` один на все типы, начинается с `1` и живёт в процессе `api`.

| `type` | Когда | `data` |
| --- | --- | --- |
| `clock` | раз в секунду реального времени, если часы известны | `seq`, `clock` |
| `vehicles` | раз в секунду реального времени, если что-то изменилось | `seq`, `clock`, `vehicles` — изменившиеся `VehicleView`, `removed` — `tr_id` пропавших ТС |
| `prediction` | на каждую строку тика | `seq`, `tr_id`, `prediction` — `PredictionView` |
| `alert` | открытие, обновление, закрытие (с шага 4) | `seq`, `alert` — `AlertView` |

Раз в секунду реального времени `api` строит `VehicleView` всех ТС,
сравнивает с опубликованными в прошлый раз и публикует разницу. Так
ловятся и переходы, у которых нет события: ТС стало `stale`, потому что
новых точек нет. Снимок отдаёт последний **опубликованный** вид и его
`seq`, а не строит новый — снимок и поток берутся из одного места.

Состояние карты меняет только `vehicles`: новый прогноз попадает на
карту с ближайшей разницей, не позже чем через секунду. `prediction`
нужен истории в открытой карточке.

Сообщения публикуют две задачи — разница раз в секунду и тик цикла.
Номер присваивается и сообщение публикуется под одной блокировкой,
поэтому в канале сообщения идут по возрастанию `seq`. Если публикация в
Redis не удалась, номер всё равно израсходован: клиент увидит пропуск и
возьмёт снимок заново.

Сбой публикатора дашборда не останавливает цикл прогноза: ошибка
пишется в лог, разница пробуется снова через секунду, а строки тика к
этому моменту уже записаны в таблицу и шину `predictions`.

Если цикл прогноза упал и перезапускается, дашборд до нового
состояния показывает последнее известное, а не пустоту.

### 7.4. Синхронизация клиента

1. Открыть `/ws`, приходящие сообщения складывать в буфер.
2. Взять `GET /api/state`.
3. Отбросить из буфера сообщения с `seq ≤ snapshot.seq`, остальные
   применить по порядку, дальше применять по мере прихода.
4. Пришло `seq ≠ предыдущий + 1` — сообщение потеряно (например, `api`
   переподключался к Redis): снова с шага 2.
5. Обрыв WS — переподключиться с паузой и начать с шага 1. После
   перезапуска `api` счётчик начинается заново, поэтому снимок берётся
   всегда.

Карточка — так же: `prediction` с `seq ≤ card.seq` пропускаются,
остальные дописываются в историю без повторов по `sample_id`. Строка
сохраняется в таблицу раньше, чем публикуется, поэтому может прийти и в
ответе карточки, и по WS.

## 9. Метрики

`GET /metrics` отдаёт JSON:

- `predict_latency_ms` — p50 / p95 / max и число вызовов `/predict` за
  последние 5 минут реального времени, со стороны `api`: от отправки
  пачки до разобранного ответа, вместе с сетью; `predict_failures` —
  сколько из них не дали ответа (ошибка, таймаут);
- `scoring_tick_ms` — длительность тика целиком, от планирования до
  публикации и алертов, p50 / p95 / max за те же 5 минут; тики без
  кандидатов не считаются;
- `stream_lag_s` — отставание обработки: сколько секунд последняя
  прочитанная запись `telemetry` пролежала в шине (время чтения минус
  время `XADD` из id записи); `null` до первой записи;
- `vehicles_active` — ТС с `freshness = active` в последнем
  опубликованном виде;
- `predictions_per_min` — строк `predictions` в минуту реального времени
  за 5 минут или с момента старта, если он позже;
- `degraded_share` — доля строк с `degraded` за те же 5 минут, `null`
  без строк;
- `alerts` — `open` / `confirmed` / `cancelled` за весь прогон и
  `mean_lead_time_s` по подтверждённым;
- `live_mae_s`, `checked_predictions` — как в снимке (§4).

Числа за 5 минут живут в памяти процесса `api`: перезапуск цикла они
переживают, перезапуск процесса — нет. Если нужен прошлый прогон,
смотреть `docs/performance.md`.

## 10. `seed`

Команда в образе `api` (`python -m app.seed`), в compose — одноразовый
сервис после `migrate`. Читает из `/data` файлы периода `seed.period`
(`test` по умолчанию — у него есть разметка для сравнения):

- расписание → `stops_plan`, **без `time_fact_begin`**;
- `traffic.csv` → пары `tr_id`, `unit_id` → `vehicles`.

Время переводится из наивного в UTC. Повторный запуск заменяет
справочники: при наличии файлов обе таблицы очищаются и загружаются
заново в одной транзакции; без датасета ничего не меняется.

## 11. Конфиг

```yaml
dataset:
  source_timezone: UTC

api:
  scoring_period_sec: 60
  stale_after_sec: 120
  drop_after_sec: 900
  predict_timeout_ms: 1000
  card_track_sec: 1800
  cors_origins: ["http://localhost:5173", "http://127.0.0.1:5173"]
  request:
    telemetry_window_sec: 1800
    schedule_back_sec: 3600
  risk:
    green: [-60, 120]
    red_above: 300

seed:
  period: test
```

Конфиг проверяется при старте: `stale_after_sec ≤ drop_after_sec ≤
request.telemetry_window_sec`. Иначе ТС, которое ещё в цикле, могло бы
остаться без единой точки в окне телеметрии. И `card_track_sec ≤
request.telemetry_window_sec`: трек карточки берётся из того же окна в
памяти и молча обрезался бы по нему.

## 12. Тесты

Каждое правило, которое легко сломать незаметно, — отдельный тест:

- целевая остановка: ровно `T + 10 мин` не выбирается, ровно
  `T + 15 мин` — выбирается; нет остановки в окне — нет запроса;
- анти-утечка: в `PredictRequest` нет телеметрии после `T` и нет факта
  остановок после `T`;
- отказ и таймаут `predictor` → fallback с `degraded`;
- устаревшее ТС → `stale_telemetry`; очень старое — выводится из цикла;
- неполное окно телеметрии → `warming_up`; старшинство причин
  `degraded_reason`;
- восстановление состояния из шин после перезапуска `api`: окно
  телеметрии и пройденные остановки те же, что до перезапуска;
- пороги риска, включая опережение;
- жизнь алерта: одно открытие на пару, подтверждение с `lead_time_s`,
  отмена, повторное открытие;
- проверка по факту: `abs_error_s` проставляется всем прогнозам на
  остановку;
- `seed` не загружает факт;
- `freshness` на границах: ровно `stale_after_sec` — `active`, ровно
  `drop_after_sec` — `stale`; позиция — из последней валидной записи,
  даже если за ней невалидная;
- текущий прогноз снимается после `StopEvent` по цели и при `offline`,
  заменяется более новым; последние прогнозы восстанавливаются из
  таблицы после перезапуска;
- разница `vehicles`: только изменившиеся ТС и `removed`; `seq` растёт
  по всем типам, в канале идёт по возрастанию и при одновременной
  публикации двумя задачами; неудачная публикация расходует номер;
  `seq` снимка — последнего опубликованного сообщения;
- снимок до старта цикла — пустой, не ошибка; карточка — `404` и `503`,
  окна трека и остановок;
- доставка `prediction` по WS через Redis;
- `WsMessage` есть в `openapi.json`.

`predictor` в тестах подменяется моком HTTP (`httpx.MockTransport`: он
уже есть в `httpx`, отдельная библиотека не нужна). Тесты с базой и
Redis — на service containers в CI, как уже устроено.

## 13. Порядок работ

1. Скелет: контракты, `system.yaml`, `seed`, таблицы бэкенда, заглушка
   `predictor`, compose с монтированием `/data`, CI.
2. Цикл прогноза с fallback и запись `predictions`.
3. `/api/state`, `/api/vehicles/{tr_id}`, WS — фронт с этого момента
   работает на живых данных.
4. Риск, алерты, проверка по факту, `/metrics`.
5. `/api/routes`, когда `matcher` даст `route_shapes`.
6. README, инструкция для жюри, Sphinx, замер в `docs/performance.md`.
