# Проверка качества метчера на CSV

Команда использует `StopDetector` из работающего сервиса. Ей не нужны
Postgres, Redis и Docker. Исходные CSV разместить в `data/dataset` без
переименования: `train/{traffic,schedule}.csv`,
`test/{traffic,schedule}.csv` и `labels/labels_{train,test}.csv`.
Содержимое `data/dataset` исключено из Git.

Из `services/matcher`:

```bash
../../.venv/Scripts/python -m app.evaluate --split train
../../.venv/Scripts/python -m app.evaluate --split test
```

Параметры детектора читаются из `config/assumptions.yaml`, часовой пояс
исходных меток — из `config/system.yaml`. Другой каталог данных и отдельный
выход можно задать через `--data-dir` и `--output`. Каждый запуск создаёт
новый каталог `data/reports/matcher/<split>-<время>`; существующий каталог
не перезаписывается.

Выход содержит `report.json` с параметрами, SHA-256 входных файлов и кода,
покрытием, MAE и ошибкой времени прибытия; `points.csv` с оценкой и эталоном
на каждой прогнозной точке; `events.csv` с найденными прибытиями,
`available_at`, отправлением и признаком восстановленного проезда.
Пропущенная оценка остаётся пустой, а MAE считается только там, где есть
оценка и эталон. Численный порог приёмки пока не задан.

План и телеметрия читаются без `time_fact_begin`, `cur_dev_s` и
`target_delay_s`. Сначала детектор воспроизводит события, затем фактические
времена и `cur_dev_s` используются для сравнения. Для точки T доступны
только телеметрия с `event_time <= T` и события, уже подтверждённые к T.
Восстановленный проезд не используется до наблюдаемого выхода из зоны.

Одинаковые времена одного ТС схлопываются с предпочтением валидной GPS-точки,
как в подготовительном офлайн-прогоне. Это проверка алгоритма на временной
последовательности; задержку доставки Redis и поведение сервиса при
перестановке входного потока она не измеряет. При разных порогах или
часовом поясе результаты сравнивать нельзя. `validate` не принимается:
для него нет эталона качества.

На выданной раздаче с параметрами текущего `config/assumptions.yaml`
получены следующие результаты:

| Метрика | Train | Test |
| --- | ---: | ---: |
| Прогнозных точек | 4434 | 353 |
| Рассчитан `cur_dev_s` | 4310 | 340 |
| MAE `cur_dev_s` на покрытых точках | 72,54 с | 63,57 с |
| Найденных прибытий | 12207 | 4051 |
| MAE времени прибытия на найденных | 27,13 с | 20,06 с |

Это метрики восстановления текущей задержки, а не качества прогноза
`target_delay_s`. Полный путь Redis → Postgres → Redis проверяется отдельными
интеграционными тестами метчера.
