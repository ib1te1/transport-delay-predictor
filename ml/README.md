# ML: прогноз задержки автобуса

Пакет `busdelay` — признаки, бейзлайны и модель для прогноза задержки на
остановке через 10–15 минут. Постановка и решения —
`docs/specs/ml-model.md`.

## Установка

Python 3.13. Из каталога `ml/`:

```
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt -r ../requirements-dev.txt
```

На Linux путь к интерпретатору — `.venv/bin/python`.

Датасет распаковать в `data/dataset/` в корне репозитория, чтобы получилось
`data/dataset/train/traffic.csv`, `data/dataset/labels/...` и так далее. Каталог
`data/` в git не попадает.

## Команды

Все запускаются из `ml/`, пути по умолчанию смотрят в `../data/`.

| Команда | Что делает | Время |
| --- | --- | --- |
| `python -m busdelay features` | таблицы признаков в `data/features/*.parquet` | ~20 с |
| `python -m busdelay arrivals` | сверка детектора прибытий с фактами | ~3 с |
| `python -m busdelay baselines` | кросс-валидация бейзлайнов | ~1 с |
| `python -m busdelay submit-baseline split_linear` | сабмит из бейзлайна в `data/submissions/` | ~1 с |
| `python -m busdelay train --name submit_v2` | CatBoost: CV, контроль, финальная модель в `models/submit_v2/` | ~5 мин |
| `python -m busdelay blend --name current --model <модели>` | среднее нескольких моделей как одна модель | ~5 с |
| `python -m busdelay predict --model ../models/submit_v2` | сабмит моделью в `data/submissions/submit_v2.csv` | ~2 с |
| `python -m busdelay check <файл>` | проверка формата сабмита | ~1 с |
| `python -m busdelay bench --model ../models/current` | задержка онлайн-прогноза на телеметрии validate | ~1 мин |

`features` нужно перезапускать после любого изменения в признаках, остальные
команды читают готовые таблицы.

## Обучение

Для сабмита и для сервиса модели разные, код и признаки у них общие:

```
# сабмит
python -m busdelay train --name submit_v2 --hint given

# сервис: среднее двух моделей в models/current/
python -m busdelay train --name current_resid --hint mix
python -m busdelay train --name current_plain --hint mix --no-residual --depth 6 --l2 3
python -m busdelay blend --name current --model ../models/current_resid ../models/current_plain
```

- `given` — подсказка `cur_dev_s` от организаторов, она же будет в validate.
- `mix` — каждая точка дважды: с подсказкой организаторов и с оценкой по
  GPS. На потоке подсказка считается по GPS, и так модель к ней
  устойчивее.
- `blend` складывает модели, обученные на тех же точках с теми же фолдами,
  в одну: деревья обеих плюс две прямые с весом 0.5. Метрики и интервал
  считаются по OOF-прогнозам участников. Остаток над прямыми точнее с
  хорошей подсказкой, модель задержки целиком — с плохой; среднее лучше
  обеих на потоке. Цифры в `docs/specs/ml-model.md`.

Синтетические борта train в обучение не идут: у каждого реального борта
есть два синтетических двойника, и модель учится находить двойника, а не
прогнозировать. Вернуть их можно `--with-synthetic`.

`train` делает три вещи:

1. Кросс-валидация на реальных бортах train+test (5 фолдов, отрезки бортов
   целиком, обе копии точки в одном фолде). Каждый фолд учится с
   `--iterations` деревьями, число деревьев выбирается по сумме кривых MAE.
2. Контроль: обучение на train, проверка на test с подсказкой организаторов
   и с подсказкой по GPS.
3. Финальная модель на всех размеченных точках с выбранным числом деревьев:
   `--seeds` моделей с разными сидами, усреднённых в один файл.

Печатает таблицу против persistence и двух прямых, метрики
классификатора «опоздание больше 2 минут» и важность признаков.

Что лежит в `models/<name>/`:

```
regressor.cbm   задержка, MAE
late.cbm        вероятность опоздания больше 2 минут
meta.json       признаки, настройки, метрики CV, интервал, важность
```

Прогнозы на отложенных фолдах пишутся в `data/oof/<name>.parquet`, а не
рядом с моделью: в них таргеты, а `models/current/` коммитится.

Опции для сравнения, каждую стоит прогнать отдельным `--name`:

| Опция | Что меняет |
| --- | --- |
| `--no-residual` | учить саму задержку, а не остаток над двумя прямыми |
| `--vehicle` | добавить номер борта как категорию |
| `--group vehicle` | в CV откладывать борта целиком: как модель переносится на незнакомый борт |
| `--with-synthetic`, `--synthetic-weight 0.5` | вернуть синтетические борта и задать их вес |
| `--seeds 1` | одна модель вместо среднего пяти, для быстрых сравнений |
| `--depth`, `--lr`, `--l2`, `--iterations` | параметры CatBoost, по умолчанию 4, 0.03, 30, 3000 |

Выбирать по строке `model` в таблице CV (MAE на реальных бортах), контроль
на test — вторым мнением.

На Windows в `cmd` вместо `python` пишется `.venv\Scripts\python`.

## Живой поток

Сервис `predictor` (`services/predictor`) вызывает
`busdelay.inference.Forecaster`. В каждом запросе от `api` приходят план
борта с начала дня и телеметрия за 150 минут до `T`; сервис ничего не
хранит между запросами. Признаки те же, что офлайн, одна функция
`point_features`: на test прогнозы сервисного пути и офлайна совпадают до
нуля (`tests/test_inference.py` проверяет то же на выдуманных данных).

Подсказки `cur_dev_s` организаторов на потоке нет, она оценивается по GPS
(`features.estimate_cur_dev`). Поэтому сервис работает с моделью
`models/current`, обученной на смеси подсказок. Как это сказывается на
точности, `train` показывает строками «cur_dev from GPS»: те же точки, где
подсказка заменена оценкой (`data/features/*_stream.parquet`).

Ответ: задержка на целевой остановке, вероятность опоздания больше
2 минут и до трёх причин по SHAP (`busdelay.explain`), каждая не меньше
15 с. Как причины переводятся в коды контракта и что нужно в запросе —
раздел 8 `docs/specs/ml-model.md`.

`busdelay.online.LivePredictor` — тот же прогноз с собственными буферами
телеметрии, на нём работает `bench`.

## Docker

```
docker build -t busdelay-ml ./ml
docker run --rm -v "$PWD/data:/data" busdelay-ml features
```

## Тесты

```
.venv/Scripts/python -m pytest
```

Тесты работают на выдуманном датасете (`tests/world.py`) и настоящих данных
не требуют.
