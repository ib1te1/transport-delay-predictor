# ML: прогноз задержки автобуса

Пакет `busdelay` — признаки, бейзлайны и модель для прогноза задержки на
остановке через 10–15 минут. Постановка и решения —
`docs/specs/ml-model.md`.

## Установка

Python 3.13. Из каталога `ml/`:

```
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt -r ../requirements-dev.txt
```

На Linux путь к интерпретатору — `.venv/bin/python`.

Датасет распаковать в `data/dataset/` в корне репозитория, чтобы получилось
`data/dataset/train/traffic.csv`, `data/dataset/labels/...` и так далее. Каталог
`data/` в git не попадает.

## Команды

Все запускаются из `ml/`, пути по умолчанию смотрят в `../data/`.

| Команда | Что делает | Время |
| --- | --- | --- |
| `python -m busdelay features` | таблицы признаков в `data/features/*.parquet` | ~20 с |
| `python -m busdelay arrivals` | сверка детектора прибытий с фактами | ~3 с |
| `python -m busdelay baselines` | кросс-валидация бейзлайнов | ~1 с |
| `python -m busdelay submit-baseline split_linear` | сабмит из бейзлайна в `data/submissions/` | ~1 с |
| `python -m busdelay train --name v1` | CatBoost: CV, контроль, финальная модель в `models/v1/` | несколько минут |
| `python -m busdelay predict --model ../models/v1` | сабмит моделью в `data/submissions/v1.csv` | ~2 с |
| `python -m busdelay check <файл>` | проверка формата сабмита | ~1 с |
| `python -m busdelay bench --model ../models/v1` | задержка онлайн-прогноза на телеметрии validate | ~1 мин |

`features` нужно перезапускать после любого изменения в признаках, остальные
команды читают готовые таблицы.

## Обучение

`train` делает три вещи:

1. Кросс-валидация на train+test (5 фолдов, отрезки бортов целиком). Каждый
   фолд учится с `--iterations` деревьями, число деревьев выбирается по
   сумме кривых MAE на реальных бортах.
2. Контроль: обучение на train, проверка на test.
3. Финальная модель на всех размеченных точках с выбранным числом деревьев.

Печатает таблицу против persistence и двух прямых, метрики
классификатора «опоздание больше 2 минут» и важность признаков.

Что лежит в `models/<name>/`:

```
regressor.cbm   задержка, MAE
late.cbm        вероятность опоздания больше 2 минут
meta.json       признаки, настройки, метрики CV, интервал, важность
oof.parquet     прогнозы на отложенных фолдах, для смешивания моделей
```

Опции для сравнения, каждую стоит прогнать отдельным `--name`:

| Опция | Что меняет |
| --- | --- |
| `--no-residual` | учить саму задержку, а не остаток над двумя прямыми |
| `--vehicle` | добавить номер борта как категорию |
| `--synthetic-weight 0.5` | вес синтетических бортов train |
| `--depth`, `--lr`, `--l2`, `--iterations` | параметры CatBoost |

Выбирать по строке `model` в таблице CV (MAE на реальных бортах), контроль
на test — вторым мнением.

На Windows в `cmd` вместо `python` пишется `.venv\Scripts\python`.

## Живой поток

`busdelay.online.LivePredictor` — то, что вызывает сервис прогноза. Держит
последние 2,5 часа телеметрии каждого борта (`add_fix`) и по запросу
(`forecast`, `forecast_all`) выдаёт:

- целевую остановку: первая с плановым временем через 10–15 минут;
- задержку с интервалом и вероятность опоздания больше 2 минут;
- цвет риска: красный от 0.6, жёлтый от 0.3;
- главную причину (`busdelay.explain`): вклады признаков по SHAP,
  собранные в понятные диспетчеру группы;
- `degraded`: `no_signal`, если данных нет дольше 5 минут, — прогноз при
  этом всё равно считается по плану и последнему состоянию.

Признаки те же, что офлайн, одна функция `point_features`. Подсказки
`cur_dev_s` на потоке нет, она оценивается по GPS
(`features.estimate_cur_dev`). Как это сказывается на точности, `train`
показывает строками «cur_dev from GPS»: контрольная модель проверяется на
test, где подсказка заменена оценкой (`data/features/test_stream.parquet`).

